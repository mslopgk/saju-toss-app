### 클라이언트 / 서버 경계

`InterpretationClient.interpret()` 가 받는 것은 **조립된 프롬프트가 아니라 `{ kind, chart, profile }`** 이다.

조립된 프롬프트가 클라이언트 → 서버 방향으로 흐르면 클라이언트가 시스템 프롬프트를 바꿔 보낼 수 있다
(프롬프트 주입). 그래서 **프롬프트는 서버에서만 만든다**. 클라이언트가 보내는 것은 차트와 자기신고 값뿐이고,
서버가 `buildInterpretationRequest()` 를 직접 호출한다.

`buildInterpretationRequest()` 자체는 `src/shared/` 에 있어 클라이언트도 import 할 수 있다. 이는
① 미리보기·오프라인 폴백(`renderTemplateInterpretation`)이 같은 팩트팩을 쓰기 위해서이고,
② `narrativeKey` 를 클라이언트가 미리 계산해 캐시 조회를 선행할 수 있게 하기 위해서다.
**API 키는 어느 경우에도 번들에 들어가지 않는다.**

v1 에 구현된 클라이언트는 `MockInterpretationClient` 뿐이다. 실제 구현
(`ServerInterpretationClient` → `POST /api/interpret`)은 서버 영역에서 붙인다.

## 2. 프롬프트 구조

### 2.1 배치와 캐시

렌더 순서는 `tools → system → messages` 이고, 캐시는 **접두사 일치**다. 그래서 배치 규칙은 하나다:
**변하지 않는 것이 앞, 사용자마다 변하는 것이 뒤.**

| 위치 | 내용 | 캐시 | 실측 크기 |
|---|---|---|---|
| `system[0..6]` | 역할 · 사실 규율 · 충돌 서술 전략 · 안전 규율 · 문장 설계 · 혈액형→말투 표 · 출력 계약 | ✅ 마지막 블록에 `cache_control` | **2,735자** (≈ 2,350 토큰) |
| `messages[0]` (user) | `fact_pack` JSON · `knowledge_cards` · 섹션 지시 | ❌ | 1,787자 (픽스처 7장 기준) |

`buildSystemBlocks()` 는 **`kind` 를 인자로 받지 않는다.** 리포트 종류별로 프리픽스가 갈리면 캐시가 종류 수만큼
쪼개진다. 종류별 차이(섹션 구성)는 user 턴에서만 지시한다.

캐시가 조용히 죽는 경로 두 가지를 테스트로 막아 두었다.
- 프리픽스에 날짜/UUID/닉네임이 들어감 → `buildRequest.test.ts` 의 정규식 검사
- 프리픽스가 최소 캐시 길이 아래로 내려감 → `staticPrefixLength() > 1024` 검사
  (Opus 5 최소 512 토큰, Sonnet 5 1,024, **Haiku 4.5 4,096**. 셋 다 미달 시 에러 없이 `cache_creation_input_tokens: 0` 이 된다.)

### 2.4 출력 스키마

구조화 출력(`output_config.format`)을 쓴다. assistant prefill 은 Opus 5 / Sonnet 5 에서 400 이므로 대안이 없다.

```json
{ "headline": "…", "sections": [{ "id": "saju", "body": "…" }], "action_today": "…", "used_card_ids": ["…"] }
```

스키마를 **두 벌** 유지한다.
- `rawInterpretationSchema` (zod): 길이 제약 포함, 응답 검증용.
- `INTERPRETATION_JSON_SCHEMA` (손으로 작성): API 전송용. Claude 구조화 출력은 `minLength`/`maxLength`/
  배열 길이 제약을 지원하지 않아 zod→JSON Schema 자동 변환을 쓰면 미지원 키워드가 그대로 나가 400 이 난다.
  두 벌의 최상위 필드가 어긋나지 않는지는 테스트가 확인한다.

**점수·등급·간지는 스키마에 없다.** LLM 이 만들 수 있는 필드가 아예 존재하지 않는 것이 가장 강한 가드다.

### 2.5 출력 검증 (`guard.ts`)

프롬프트로 부탁하는 것과 출력을 검사하는 것은 다른 층이다. 다섯 단계 전부 결정론적이다.

| 코드 | 검사 |
|---|---|
| `SCHEMA` | zod 파싱 (길이·타입) |
| `SECTION_MISMATCH` | 섹션 집합과 **순서**가 지시와 정확히 같은가 |
| `UNKNOWN_CARD` | `used_card_ids` ⊆ 프롬프트에 넣은 카드 id |
| `BANNED_PHRASE` | 14종 금지 표현(과학적 주장·단정 예언·의료·재무·법적 결과·관계 낙인). 완곡 부정형("반드시 ~인 것은 아닙니다")은 오탐 제외 |
| `FABRICATED_GANJI` | 본문의 `천간+지지` 인접 2글자가 원국 4주 · 대운 간지 집합에 없으면 환각 |
| `FABRICATED_NUMBER` | `N점` / `N%` 의 N 이 팩트팩 수치 집합에 없으면 환각 |

거부 시 화면이 비지 않는다 — `renderTemplateInterpretation()` 이 같은 팩트팩으로 규칙 문장을 렌더한다
(문서10 §5.1 [3] 문장 조립 레이어). `MockInterpretationClient` 가 그대로 이 폴백 경로다.

## 3. 왜 계산은 RAG 로 하지 않는가

지식 카드 검색은 **해석 문장의 근거**에만 쓰고, **숫자에는 쓰지 않는다.** 이유 다섯 가지.

**① 정답이 이미 있다.** 사주 계산은 열린 질문이 아니라 결정 절차다. C00 은 절기(UTC 절대순간 비교), 일주
(`(JDN_정오 − 11) mod 60`), 십신 룩업, 신강신약 계수를 전부 고정했다. 정답 함수가 있는 문제에 근사 검색을
끼우면 정확도가 내려가기만 한다.

**② 결정론이 제품 요구사항이다.** C00 §F7 은 엔진에서 `Date.now()`·`Math.random()`·`Intl` 을 금지하고,
§7.4 는 출력 실수까지 양자화하도록 요구한다. 같은 사람이 다시 열었을 때 신강지수가 58.4 에서 59.1 로 바뀌면
그 순간 서비스 신뢰가 끝난다. LLM 은 같은 입력에 같은 출력을 보장하지 않는다.

**③ 검증 체계가 계산에만 존재한다.** C00 §6 은 4층 검증(불변식 → 골든셋 1,207 테스트 → 전수 검증 →
독립 오라클 3자 대조)을 규정한다. LLM 이 숫자를 만들면 이 검증 자산이 통째로 무의미해진다.

**④ 비용·지연이 반대다.** 계산은 1 ms 미만이고 0원이다. 같은 일을 LLM 에 시키면 건당 수십~수백원에
1~5초가 든다. 게다가 계산이 캐시보다 싸므로(C00 §7.2) 클라이언트에서 그냥 다시 계산하면 된다.

**⑤ 환각의 손해가 비대칭이다.** 문장이 어색한 것은 품질 문제지만, 없는 신살을 언급하거나 원국에 없는
간지를 말하는 것은 사실 오류다. 그래서 계산은 규칙이 확정하고, LLM 은 확정된 사실을 문장으로만 옮긴다
(문서10 §5 하이브리드 C안).

**그럼 카드는 왜 검색하는가.** 서술 근거(일간 상징, 별자리 기질, 십신 해석)는 정답 함수가 없는 텍스트
자산이고, 전부 프롬프트에 넣으면 토큰이 폭발한다. 그래서 팩트팩에서 뽑은 태그로 **정확일치 검색**을 한다.
임베딩·벡터 검색이 아닌 이유는 ① 모델 버전이 바뀌면 결과가 흔들려 캐시 키가 깨지고, ② 대상이 수천 건
수준이라 근사 최근접이 필요 없으며, ③ 어떤 카드가 왜 뽑혔는지 QA 에게 설명할 수 있어야 하기 때문이다.

문서11 §6.3 의 124원과 134원의 차이는 **정적/동적 배분이 다르기 때문**이다. 문서11 은 MBTI 16유형표·별자리
12·혈액형 4 참조 테이블(약 1,600 토큰)을 정적 프리픽스에 넣어 5,500 토큰을 캐시했지만, 이 구현은 그 내용을
**사용자별로 검색되는 지식 카드**로 옮겼다(정확도·근거 추적성 때문). 캐시 토큰은 0.1× 라서 정적→동적 이동은
그만큼 비싸진다.

**개선 후보 (미적용)**: 어차피 사용자와 무관하게 고정인 카드(별자리 12·혈액형 4·MBTI 16)를 정적 프리픽스로
되돌리면 정적 ≈ 3,950 / 동적 ≈ 2,550 이 되어 건당 **$0.0847 (약 123원)** 로 약 8% 절감된다. 대신
"카드에 없는 내용 금지" 규칙의 경계가 흐려지므로, 근거 추적성을 유지할 수 있는지 확인한 뒤에 적용한다.

- `daily` 는 규모가 커지면 지배적이 되므로(문서11 §6.5) 개인화 축을 줄여 사전생성해야 한다. v1 미구현.

## 5. 캐시 키

```
narrativeKey = PROMPT_VERSION | engineVersion | kind | chartIdentityKey(chart)
             | g=성별 | mb=MBTI | bl=혈액형 | k=fnv1a32(카드 id 목록)
```

문서10 §5.2 는 `{일간}|{MBTI}|{혈액형}|{별자리원소}` 4축(2,560 엔트리)을 제안하지만 **그대로 쓰면 안 된다**:
현재 프롬프트는 팩트팩 전체(gz8·대운 10기·신살)를 주입하므로, 4축만으로 캐시하면 **간지가 다른 사람에게
같은 문단이 나간다**. 그래서 엔진이 `chart.cacheKey`(C00 §7.3 L1 키)를 주면 그것을 축으로 그대로 쓴다.

> ⚠ 엔진 v1(`SAJU-ENGINE-1.0.0`)은 아직 `cacheKey` 를 만들지 않는다. 없으면 `chartIdentityKey()` 가
> 차트의 정체성 필드(gz8 · 삼주 여부 · 대운 전체 · 경고)만 골라 `x:` 접두의 결정론적 대체 키를 만든다.
> 엔진이 캐시키를 내기 시작하면 접두가 사라지므로 그 시점에 캐시가 한 번 통째로 무효화된다 — 의도된 동작이다.
>
> 경고 중 **`LUNAR_CONVERTED` 는 축에서 뺀다**(`NON_IDENTITY_WARNINGS`). 그건 차트가 아니라 **입력 출처**의
> 사실이고, 같은 양력일을 음력으로 넣은 사람과 양력으로 넣은 사람은 같은 사주라 같은 서사를 받아야 한다
> (C00 §7.3 규칙 1 · §S0-2 b). 넣으면 같은 명식이 두 키로 갈려 그 규칙을 코드가 직접 위반한다.
> 회귀는 `test/saju/lunar.test.ts`「캐시 키」가 막는다.

- 교차 사용자 재사용은 L2 가 아니라 **L1 차트 캐시**에서 나온다(같은 생년월일시·출생지면 같은 차트 키).
- 카드 집합을 FNV 해시로 축에 넣어 **지식베이스를 개정하면 자동 무효화**되게 했다.
- sha256 대신 평문 조합을 쓴 이유: WebView 의 `crypto.subtle` 은 비동기라 순수함수 안에서 쓸 수 없고,
  이 키에는 PII 가 없어 가릴 이유도 없다(디버깅에는 오히려 유리).
- `PROMPT_VERSION` 또는 `engineVersion` 이 바뀌면 전체 무효화된다. 프롬프트 문구나 출력 스키마를 바꾸면
  `PROMPT_VERSION` 을 올린다.

**v2 후보**: 팩트팩에서 개인 고유 사실(gz8·대운·신살)을 빼고 "구조 동치류"만 남기면 4축 축약 키로 돌아갈 수
있어 히트율이 크게 오른다. 대신 개인 고유 사실은 계층1 규칙 문장 슬롯이 렌더해야 한다.

## 7. 지식카드 계약 (통합 확정)

카드 타입의 **정본은 `shared/knowledge/types.ts`** 하나다. 해석 레이어(`contracts.ts`)는 재수출만 한다.
예전에는 `interpret/contracts.ts` 가 `{ system, body, evidenceGrade }` 모양의 두 번째 `KnowledgeCard` 를
따로 선언했고, 실제 지식베이스(`{ kind, summary, detail, confidence }`)와 필드가 전혀 겹치지 않아
`selectKnowledgeCards()` 가 항상 빈 배열을 냈다. 두 벌을 없애 그 경로를 지웠다.

### 7.1 본문 필드 — `detail` 을 쓴다

`summary` 는 추출값을 끼운 결정론적 한 문장이라 팩트팩과 내용이 겹친다. 같은 사실을 두 번 주면 토큰만
늘고, 모델이 "카드가 그 수치의 출처"라고 착각할 여지가 생긴다. 프롬프트에 나가는 본문은
`cardBody(card)`(= `detail`) 하나로 고정했다.

### 7.2 태그 규약 — 값 표기는 **엔진 출력이 정본**

카드 `tags` 는 손으로 적지 않는다. `scripts/build-knowledge.mjs` 의 `tagsOf(kind, key)` 가 만들고,
질의 쪽은 `retrieve.ts` 의 `queryTagsOf(fact)` 가 만든다. 두 문자열이 글자 단위로 같아야 매칭된다.

통합 전에 어긋나 있던 지점과 확정:

| 축 | 어긋난 모양 | 확정 |
|---|---|---|
| 별자리 | 질의 `zodiac:사자자리` vs 카드 key `leo` | **사인 id** (`zodiac:leo`). 팩트팩에 `sunSignId` 를 추가했다 |
| 용신 도출 경로 | 질의 `yongsinRoute:抑扶+格局` vs 카드 key `용신5법:억부(抑扶)` | **엔진 유니온** (`抑扶+格局`). 빌드 스크립트가 카드 표기를 유니온으로 매핑한다 |
| 십신 | 질의는 5그룹(`재성`) vs 카드 key 는 10신(`편재`) | 카드가 **두 태그를 함께** 단다 (`sipsin:편재` + `tenGod:재성`). 질의도 **두 축을 함께** 낸다 — 그룹 축이 후보를 넓히고, 10신 축(`fact.saju.tenGodNames`)이 원국에 실재하는 십신을 2히트로 앞세운다 |

**인지기능 8장은 새 축 없이 열었다.** 팩트팩은 4글자 코드만 들고 스택을 계산하지 않는다(계산하면
`personality-data.json` 의 스택 표가 두 벌이 된다). 대신 `build-knowledge.mjs` 가 인지기능 카드에
그 기능을 스택에 가진 16유형의 `mbti:{코드}` 태그를 함께 달아, 이미 있는 축으로 닿게 했다.
`dayElement`·`monthElement` 는 `tables.json` 룩업이다 — 표를 코드로 옮겨 적지 않는다(C00 §F6).

**저작 규칙 카드 2장(`fusionCopy:*`)의 경계.** 저작 규칙은 원칙적으로 "사용자에 대한 사실"이 아니라
검색 대상이 아니다. 예외는 `daewoonNote:*`(만나이 표기·5년 분할 금지)가 이미 만들어 둔 것과 같다 —
그 규칙이 **사용자가 화면에서 겪는 선택**을 정하고, 그 선택을 리포트가 실제로 한 문장으로 밝히는 경우에는
출처를 인용한다. 두 카드가 정하는 선택은 각각 이렇다:

| 카드 | 정하는 선택 | 밝히는 자리 |
|---|---|---|
| `fusion:카피:4단구조` (문서10 §6.2) | 각 항목을 **어떤 순서로 읽게 되는가**(관찰 → 양면 → 오늘 한 가지) | `saju` 섹션 끝 한 문장. ④는 섹션이 아니라 `actionToday` 블록이라 문장도 거기까지 가리킨다 |
| `fusion:카피:금지어` (문서10 §6.3) | **무엇을 말하지 않는가**(단정 예언·의료 유사 표현) | `luck` 섹션 끝 한 문장. 사용자가 예언을 기대하는 자리가 그곳이다 |

금지 표현을 예시로 **인용하지 않는다** — 인용하는 순간 그 문자열이 본문에 실려 `guard.ts` 의
`findBannedPhrases()` 에 걸린다. 규칙을 지키는지는 그 검사기가 800+ 사주 스윕에서 0건으로 고정하므로,
`luck` 섹션의 문장은 바람이 아니라 검증된 사실이다.
반대로 **밝히지 않는** 저작 규칙(`fusion:일치도:*` 라벨)은 검색하지 않는다. 조회만 하고 대응 문장이 없으면
화면의 "이 리포트가 참고한 자료"에 제목만 뜨고 사용자는 그 카드가 무엇을 했는지 알 수 없다.

**닿지 않는 20장**은 `retrieve.test.ts` 의 `UNREACHABLE_CARD_IDS` 에 **id 낱장으로** 못박혀 있다.
축 단위 대조(`CARD_ONLY_AXES`)는 "축이 어긋났다"까지만 잡고, 축은 맞는데 값 표기가 어긋나 카드가
통째로 노는 상태는 잡지 못하기 때문이다.

| 미도달 | 장수 | 사유 |
|---|---|---|
| `daewoon:관계:*` | 15 | 사유가 **둘**이고 둘 다 혼자서도 결정적이다. ① 대운 간지 × 원국의 합·충 이벤트 판정(C06 §7.3)을 엔진이 내지 않는다 — 원국 **내부** 합충(`chart.sinsal.branchRelations`)은 있지만 이 카드들은 "운과 원국 사이"를 서술한 것이라 바꿔 쓰면 뜻이 달라진다. ② 판정이 생겨도 카드 본문이 통째로 운 점수 가중표(`천간합 +6` · `지지충 -10` · `clamp(-25,+25)`)라 서술 재료가 아니다. 그 수치는 팩트팩에 없으므로 본문에 쓰면 `numberAllowList` 가 지어낸 수치로 거부한다 |
| `fusion:일치도:*` | 4 | 구간을 고르려면 0~100 Coherence 점수(문서10 §3.2)가 필요한데 그 지표의 정의가 C00 에 없다. 렌더러가 만들면 `factPack.ts` 의 규율("일치도 점수는 계산 엔진의 몫")을 정면으로 어긴다. **C00 변경 제안 대상**이다 |
| `yongsin:용신5법:병약(病藥)` | 1 | 엔진이 5관 病藥 게이트를 **실제로 돌린다**(`strength.ts` §5관 — 藥 오행을 희신 뒤에 덧붙인다). 그런데 `route` 는 여전히 `抑扶+格局` 이고, 게이트 발동 여부는 `yongsin.steps` 의 **한국어 로그 문자열**에만 남는다. 로그를 파싱하면 같은 판정의 출처가 두 벌이 되고 엔진 문구가 바뀌는 날 조용히 끊긴다 → 파싱하지 않는다. **엔진 변경 제안 대상**이다 |

도달 수의 바닥은 `e2e.test.ts` 의 도달률 회귀가 실제 사주 스윕(≈2,200건)으로 고정하고, 같은 테스트가
**문장에 실제로 인용되는 수(173장)** 도 함께 잰다. 검색만 되고 한 번도 인용되지 않는 카드는
"도달했다"고 보기 어렵고, 그 상태는 검색 테스트만으로는 드러나지 않는다.
남는 5장은 의도된 것이다 — `blood:{A,B,O,AB}` 4장(성격 판정에 쓰지 않기로 한 통념 카드)과
`fusion:오행MBTI:토(土)` 1장(문서10 §2.1 에서 土 만 "중립"이라 견줄 글자가 없다).

### 7.3 없는 섹션은 없다고 말한다

지금 엔진은 신살(S4-2)·신강신약(S5)·별자리(S7)를 **모두 채운다**(캐시키만 아직 없다). 그래도
`ChartLike` 에서 셋 다 옵셔널로 남긴다 — 저장된 구버전 결과·픽스처가 들어와도 해석 레이어가 깨지면
안 되기 때문이다. 그때 `buildFactPack()` 은 해당 섹션을 `null` 로 두고 `FactPack.missingSections` 에
이름을 남기며, 그 섹션은 리포트에서 그냥 사라진다. `queryTagsOf()` 도 없는 섹션의 태그를 만들지 않는다.
(실제 `computeChart()` 출력에서는 `missingSections` 가 항상 빈 배열이다 — `e2e.test.ts` 가 고정한다.)

`sinsalNames` 가 `null` 인 것과 `[]` 인 것은 다르다 — 전자는 "계산하지 않았다", 후자는 "신살이 없다"다.

### 7.4 화면에 나가지 않는 값

`tenGodWeights`(엔진 `groupWeights`)는 팩트팩에는 남기되 `numberAllowList()` 에서 **뺐다**. 엔진이
C00 §S4-1 에서 "임시 정의"라고 밝힌 가중치라 `78점` 같은 형태로 문장에 나가면 안 된다. 결과 화면도
같은 이유로 십신은 **이름만** 보여주고 가중치 숫자는 표시하지 않는다. `dominantTenGod`(그룹 이름)은
순위 비교 결과라서 그대로 쓴다.

## 9. 규칙 기반 리포트 (`template.ts`) — 화면이 실제로 쓰는 경로

LLM 도 서버도 없이 읽을 만한 리포트를 만든다. 문서10 §5.1 의 **[3] 문장 조립 레이어**에 해당하며,
[4] 윤문 레이어(LLM)는 서버가 붙은 뒤에 얹는다.

```
Chart ──buildFactPack──▶ FactPack ──selectKnowledgeCards──▶ KnowledgeCard[]
                              └──────────┬─────────────────────┘
                                         ▼
                            renderTemplateReport(fact, cards) → Interpretation
                                         ▼
                            features/report ──▶ ResultPage (ReportView)
```

### 9.1 무엇이 어디서 오는가

| 조각 | 출처 | 이 파일이 만드나 |
|---|---|---|
| 간지·나이·십신 이름·gz8 | 팩트팩(= 계산 엔진) | ❌ 그대로 옮긴다 |
| 성향·강점·주의·직업 재료·인지기능 스택·띠·절기월 | 지식카드 `detail` 의 `라벨 — 값` 슬롯 | ❌ 추출한다 |
| 접속 문장·안전 고지·행동 제안 골격 | 이 파일 | ✅ |
| 혈액형 어조(여는/닫는 한마디) | 이 파일의 4행 표 + 문체 카드의 라벨 | ✅ 말투만 |

즉 **실질 주장은 전부 카드에서 오고, 이 파일은 그 조각을 잇는다.** 근거 카드 id 는 `usedCardIds` 에 남고
`ReportView` 가 카드 제목·출처 문서·근거등급을 화면에 표시한다.

### 9.2 섹션 구성 — 근거가 있는 것만

`SectionId` 에 `sipsin`·`jiji`·`sinsal` 을 추가했다. 기존 `saju` 하나에 눌러 담으면 근거가 다른
이야기(일간 룩업 / 십신 룩업 / 지지 룩업 / 신살 판정)가 한 덩어리가 된다. LLM 경로의 섹션 구성
(`SECTIONS_BY_KIND`)은 바뀌지 않았다 — **스키마는 공유하되 어떤 섹션을 채우는지는 경로마다 결정한다.**

렌더 순서는 문서10 §8 리포트 IA 를 따른다: 체계별 카드(사주 → 별자리 → MBTI → 혈액형)를 먼저
늘어놓고, 체계를 **가로지르는** 두 섹션(교집합 → 충돌)이 마지막에 온다. 가로지르는 이야기가 먼저 오면
독자가 아직 각 체계에서 무슨 값이 나왔는지 모르는 상태에서 "공통점"을 읽게 된다.

| # | 섹션 | 필요한 카드 | 없으면 |
|---|---|---|---|
| 1 | `saju` | `ilgan:{일간}` | 섹션 없음 |
| 2 | `sipsin` | `sipsin:{원국에 있는 십신}` | 섹션 없음 |
| 3 | `jiji` | `jiji:{일지}` 또는 `jiji:{월지}` | 섹션 없음 |
| 4 | `sinsal` | `sinsal:{엔진이 판정한 이름}` | 신살이 없거나 카드가 없으면 섹션 없음 |
| 5 | `strength` | 없음(엔진 S5 값만으로 선다) + `unseong:*`·`yongsin:격국:*`·`yongsin:용신5법:*`·`yongsin:억부:*`·`yongsin:신강지수:*` | 팩트팩에 `strength` 가 없으면 섹션 없음 |
| 6 | `luck` | 없음(대운 간지·나이·방향만) + `daewoon:방향:*`·`daewoon:서술:*` | 대운이 비면 섹션 없음 |
| 7 | `zodiac` | `zodiac:{사인id}` 또는 `zodiac:원소:{원소}` + `fusion:통합:별자리중복` | 팩트팩에 `astro` 가 없으면 섹션 없음 |
| 8 | `mbti` | `mbti:{4글자}` + `mbti:축:*` + `mbti:인지기능:{주기능}` + 자기신고 | 섹션 없음 |
| 9 | `blood` | `blood:문체:{형}` + 자기신고 | 섹션 없음 |
| 10 | `intersection` | 일치한 축 ≥1 **또는** 공통 키워드 ≥1 | 섹션 없음 |
| 11 | `conflict` | 갈린 축 ≥1 | 섹션 없음 |

"준비 중입니다" 같은 빈 섹션은 렌더하지 않는다 — 화면에 빈 자리를 남기는 것보다 섹션이 없는 게 낫다.

#### 9.2.1 신살 섹션이 말하는 것 / 말하지 않는 것

말하는 것은 넷뿐이다: **이름 · 길흉 분류 · 걸린 기둥 · 카드의 키워드**. 이름과 기둥은 엔진 값이고
(`FactPack.sinsalHits`), 길흉은 카드 제목 꼬리(`천을귀인(天乙貴人) — 길신`)에서 읽는다.
점수(`SinsalHit.score`)는 **팩트팩에 담지도 않는다** — 담아 두면 언젠가 문장으로 샌다.
자세히 보는 두 장은 **길신 → 십이신살 → 흉신** 고정 순서로 고른다. 엔진 배열 순서를 그대로 쓰면
우연히 흉신 두 장이 앞에 와서 섹션이 경고문처럼 읽히는데, 문서10 §6.4 는 주의를 1할로 묶는다.
마지막 문장이 경계를 사용자에게도 밝힌다 — 카드 본문이 직접 요구하는 규율이다
("원문에 없는 구체 사건(질병·사고 등) 단정은 금지").

#### 9.2.2 별자리 섹션 — 중복성 고지가 부품이다

태양궁은 사주 월지를 약 15일 시프트한 **같은 12분할**이다(문서10 §2.6). 그 사실을 빼면 별자리가
"정보가 하나 더 늘었다"로 읽히므로, `fusion:통합:별자리중복` 카드를 근거로 매 리포트에 고지한다.
생시를 모르면 달 별자리는 12:00 가정값이고(C00 §3-G15) 그 사실도 함께 적는다. ASC 는 엔진이 항상
`null` 이라(정보량 0) 등장하지 않는다.

#### 9.2.3 융합 두 섹션 — 점수 없이 견주기

문서10 §3.2 는 일치도(Coherence)를 0~100 으로 계산해 히어로로 쓰라고 한다. **그 지표는 만들지 않았다.**
정의가 C00 에 없고, `factPack.ts` 의 설계 원칙이 "일치도 점수는 계산 엔진의 몫"이라고 이름까지 짚어
금지하고 있기 때문이다(그래서 `fusion:일치도:*` 4장이 미도달로 남는다).

대신 **글자 하나의 같고 다름**만 본다. 대응표는 전부 카드가 들고 있고 렌더러는 읽어서 견주기만 한다.

| 축(카드 key 와 같은 이름) | 왼쪽 | 오른쪽 | 대응표 출처 |
|---|---|---|---|
| `사주 vs MBTI 상충` | 일간 오행의 E/I | 자기신고 코드 1번째 글자 | `fusion:오행MBTI:*` 의 `학술 근거 매핑` |
| `별자리 원소 vs MBTI` | 태양궁 원소의 융 4기능 글자 | 코드 2번째(N/S) 또는 3번째(T/F) 글자 | `zodiac:원소:*` 의 제목 |
| `사주 내부 상충` | 일간 오행의 E/I | 월지 오행의 E/I | 같은 `fusion:오행MBTI:*` 두 장 |

- **일치한 축 → `intersection`, 갈린 축 → `conflict`.** 비교가 성립하지 않으면(카드가 없거나 오행이
  중립(土)이거나 자기신고가 없으면) 그 축은 아예 빠진다 — "비교했는데 같았다"와 "비교할 수 없었다"는
  다른 사실이다.
- 검색 태그는 **"그 비교를 할 수 있는가"** 로만 발행하고 "어긋났는가"는 보지 않는다. 판정을 검색으로
  끌어오면 대응표가 두 벌이 된다. 검색은 재료를 모으는 층, 서술이 결과를 읽는 층이다(문서10 §5.1).
- 충돌은 **한 번에 한 축만** 짚는다(제목이 "딱 하나"다). 어느 것을 고를지는 위 표의 고정 순서가
  정한다 — 크기를 재서 고르면 만들지 않기로 한 일치도 점수가 뒷문으로 들어온다.
- 충돌 서술은 **어느 하나를 부정하지 않는다**(문서10 §3.3 3원칙). "A인데 B다"가 아니라 "겉은 A, 안은 B",
  시간축·상황축으로 나눈다. 프레임 이름은 카드의 `서술 전략` 에서 온다.
- 공통 키워드(§3.4)는 **배지 숫자를 만들지 않고** 어느 체계가 같은 말을 했는지 이름으로만 적는다.
  후보는 사주·별자리·MBTI 세 체계뿐이다 — 혈액형은 가중치 0(§3.1)이고, 혈액형 통념 카드의 키워드가
  교집합에 섞이면 바로 "혈액형으로 성격을 말하는" 짓이 된다. 두 글자 이상 한글만, 자기 카드 제목에
  들어 있는 낱말은 제외한다(MBTI 자체 별칭이 새는 경로도 이 두 거름이 함께 막는다).
- 두 섹션이 다 없는 경우는 견줄 축이 하나도 없는 사주다(예: 土 일간 + 자기신고 없음). 가로지르는
  고지(혈액형 가중치 0 · 세 체계 면책)는 두 섹션 중 **정확히 한 곳**에서만 나온다.

### 9.3 카드를 한 번 더 거르는 이유 (`tenGodNames`)

검색은 십신 **그룹** 태그(`tenGod:재성`)로 한다. 그러면 재성 그룹의 두 카드(`sipsin:정재`,
`sipsin:편재`)가 **둘 다** 뽑히는데, 원국에는 편재만 있을 수 있다. 그 카드로 문장을 쓰면 없는 사실이 된다.
그래서 팩트팩이 `tenGodPlacements`(기둥별 룩업 결과)와 `tenGodNames`(원국에 실제로 있는 십신)를 내고,
렌더러가 후자로 카드를 건다. `template.test.ts` 가 1993-05-16 차트로 이 경로를 고정한다
(`sipsin:정재` 는 검색되지만 `usedCardIds` 에 없다).

### 9.4 카드 본문에서 **쓰지 않는** 라벨

`OMITTED_FIELDS`. 대부분 "쓰면 사실이 아니게 되는" 것들이다.

| 라벨 | 이유 |
|---|---|
| `빈도` · `국내 분포` | 표본 비율(`5.37%`)·인구 비중(`34%`)은 팩트팩에 없는 수치 → `FABRICATED_NUMBER` |
| `점수 축` | 내부 배점 재료. 화면에 나가면 근거 없는 점수로 읽힌다 |
| `지장간` | 계산 재료이지 서술 근거가 아니다 |
| `육친` | 가족 관계 단정으로 읽힌다("남 이복형제·경쟁자") |
| `억부 방향` | 조건문 그대로다("신약이면 A, 신강이면 B"). S5 가 조건을 이미 풀었고 풀린 결과는 `strength` 섹션이 엔진 값으로 말한다. 조건문을 함께 실으면 조후·종격 경로의 용신과 어긋나 보인다 |
| `일간 기준 신살 자리` | 일간별 **자리표**(어떤 지지에 붙는지)다. 실제로 붙었는지는 엔진 S4-2 가 판정하고 `sinsal` 섹션이 그 결과로 말한다. 자리표를 함께 실으면 안 붙은 신살까지 말하게 된다 |
| `전통 천문 방위 대응 서양 12궁` · `전통 천문 방위 대응` | 방위 대응이라 "띠=별자리"로 읽히면 오해다(카드 본문도 그렇게 못박는다). 지지 카드·별자리 카드 양쪽에서 막는다 |
| `대중 통념` | 혈액형 성격론. C18 이 반증을 확정했다 |
| `판정 규칙` · `판정` | 신살 판정 절차(구결 한문 「甲戊庚牛羊…」, 삼합국 墓地 순환). 일부는 자료 객체가 문자열로 굳어 `[object Object]` 다 |
| `근거` · `근거 등급(tables.json)` | 대조한 원전·라이브러리 목록. QA 추적용이고 화면 근거는 카드 제목·출처가 맡는다 |
| `정규화 공식` | 오행→축 사영 공식(`E_score=(목+화)/8 …`). **우리는 이 값을 계산하지 않는다** — 실으면 계산한 척이 된다 |
| `근거 구분` · `확장 매핑(제품용)` | 편집 메모와 [창작 필요]로 표시된 확장 매핑. 학술 근거 매핑과 섞이면 근거 등급이 흐려진다 |
| `예시 상황` · `문장 템플릿` | 충돌 카드의 예시는 남의 사주고, 원문 템플릿은 `{A}`·`{계절}` 슬롯을 다 채우지 못하면 중괄호가 그대로 화면에 나간다 |
| `본 앱 결정` | 대운 나이 카드의 내부 결정문(`startAgeWestern·startAgeKorean 둘 다 보관`). 코드 식별자다 |

추가로 `(C03 §1.1)` 같은 인용 괄호, `[창작 필요]` 같은 편집 주석, `⚠️`/`※` 로 시작하는 줄은
본문에서 지운다. **MBTI 카드의 제목은 쓰지 않는다** — 16유형 별칭이 NERIS 저작물이라는 경고가
카드 본문에 붙어 있다(문서05).

### 9.5 혈액형 = 말투만

C18(縄田健悟 2014, n=11,729)이 혈액형 성격론을 반증했다. 그래서 혈액형이 정하는 것은 두 자리뿐이다:
**첫 섹션의 여는 한마디**와 **마지막 섹션의 닫는 한마디**. 문구는 문체 카드가 선언한 라벨
(`차분·정리형` / `발랄·직설` / `활기·행동유도형` / `아이러니·양면 서술`)에 맞춘다 — 카드가 말하는 문체와
실제 문장이 어긋나면 혈액형 섹션의 설명이 거짓이 된다.

문장 전체를 4벌로 만들지 않았다: 같은 사실을 4번 적으면 어느 한 벌만 고쳐지는 날이 오고, 결정론 검증
대상도 4배가 된다. 어조를 두 자리로 좁혀도 "말투만 바꾼다"는 약속은 지켜진다.
성격 서술 카드(`blood:{형}`)는 검색되지만 **근거로 쓰지 않는다**(`blood:문체:{형}` 만 쓴다).

## 10. 서버 배선 (`../server`)

§1 이 "서버 영역에서 붙인다"고 남겨 둔 부분이 실제로 붙었다. 서버는 **앱과 별도 패키지**
(`server/package.json`)이고, 프롬프트·지식카드·API 키를 전부 자기 쪽에만 둔다.

```
WebView                                   server/ (Node · node:http)
  computeChart()                            zod 검증 (선언 안 한 키는 버림)
      │                                       → buildFactPack()            ┐
      ├─ POST /api/interpret ────────────▶    → selectKnowledgeCards()     │ 전부
      │   { kind, chart, profile }            → buildInterpretationRequest()│ app/src/shared/interpret
      │                                       → [narrativeKey 캐시]         │ 경로 참조(복붙 아님)
      │                                       → Anthropic Messages API      │
      ◀── 200 {status,source,value} ─────     → verifyInterpretation()      ┘
      │   422 {status:"rejected"} / 5xx
      └─ 실패하면 규칙 기반 리포트 그대로
```

### 10.1 왜 클라이언트가 프롬프트를 보내지 않는가

§1 의 결정 그대로다. 바뀐 것은 그 결정을 **파일 경계로 못박았다**는 점이다.

| 파일 | 값(runtime) import | 역할 |
|---|---|---|
| `shared/interpret/clientFetch.ts` | **0개** | `ServerInterpretationClient`. 타입만 가져오고 검증도 zod 없이 손으로 한다 |
| `features/report/useInterpretation.ts` | `ui` · `buildReport` | 규칙 기반을 먼저 그리고 서버 문장이 오면 갈아 끼운다 |

`clientFetch.ts` 가 그래프의 **잎**이어야 하는 이유: 화면이 LLM 경로를 쓰려면 이 파일을 import 하는데,
여기가 값으로 조립기(`buildRequest.ts`)나 목 클라이언트(`client.ts`)에 닿는 순간 시스템 프롬프트가
미니앱 번들에 실린다. `ui.test.ts` 는 `ui.ts` 에서 출발한 폐쇄만 고정하므로 이 파일은 그 그물에
걸리지 않는다 — 그래서 `clientFetch.test.ts` 가 자기 import 목록을 따로 훑는다.

### 10.2 폴백이 기본값이다

화면은 **언제나 규칙 기반 리포트를 먼저 그린다.** 서버 문장은 나중에 덧칠된다.

| 상황 | 화면 | 고지 |
|---|---|---|
| `VITE_INTERPRET_API_BASE` 미설정 | 규칙 기반 | 없음(폴백이 아니라 정상이다) |
| 요청 중 | 규칙 기반 | "해석을 조금 더 다듬는 중이에요" |
| 200 + 검증 통과 | 서버 문장 | 없음 |
| 422 · 5xx · 타임아웃 · 네트워크 실패 | 규칙 기반 | "지금은 기본 해석으로 보여 드리고 있어요" |

로딩 스피너를 띄우고 기다렸다 실패하면 빈 화면이 되지만, 완성된 리포트를 띄워 두고 교체하면
**실패가 사용자에게 보이지 않는다.** 그래서 서버 미배포가 곧 "LLM 없이 동작하는 앱"이다.

클라이언트 타임아웃은 60초다. 넘어서 폴백으로 남더라도 **서버는 계산을 끝내 캐시에 넣으므로**
다음 진입에서 즉시 뜬다. 실패한 첫 방문이 두 번째 방문의 예열이 되는 구조다.

### 10.3 프롬프트 주입 — 세 겹

팩트팩은 차트 필드를 그대로 user 턴에 직렬화한다. 즉 `mbti`·`geokguk.name`·`sinsal[].name` 은
**클라이언트가 보내는 프롬프트 조각**이다. 길이만 재고 통과시키면 그 자리에 지시문을 넣을 수 있다.

1. 조립된 프롬프트는 클라이언트→서버 방향으로 흐르지 않는다(§1)
2. zod 가 **선언하지 않은 키를 버린다** → 엔진 `Chart` 의 나머지(입력 원본·JDN·중간 계산)는 프롬프트에 닿지 않는다
3. 자유 문자열은 **문자 집합까지** 좁힌다 — MBTI 는 16유형 정규식, 간지는 60갑자, 신살명·격국명은 한글·한자·괄호만

### 10.4 실측으로 드러난 것 — §4 의 토큰 추정이 낮았다

`server/scripts/smoke.ts` 가 실제 조립기를 통과시켜 잰 값(fusion · 카드 14장):

| 구성 | §4.2 추정 | **실측 문자** | 차이 |
|---|---:|---:|---|
| 정적 프리픽스 | 2,735 | **2,735** | — |
| fact_pack | ≈ 1,600 | **2,363** | +48% (S5·신살·대운이 실제로 채워졌다) |
| 지식 카드 + 지시 | ≈ 3,200 | **4,958** | +55% (카드 한 장이 250자가 아니라 354자다) |
| **입력 합계** | ≈ 7,535 | **10,056** | **+33%** |

건당 원가는 **149원 → 165원**(캐시 미스) 수준으로 올라간다. 계산 근거와 시나리오별 표는
`server/README.md` §원가. 토큰 열은 여전히 0.86 tok/char 환산 추정이며, `count_tokens` 실측은
키가 주입된 뒤 `npm run smoke -- --tokens-only` 한 번으로 끝난다(§6 I7).

§6 I8(정적 참조표를 프리픽스로 되돌리기)의 기대 절감폭도 이 실측으로 다시 계산해야 한다 —
동적 카드가 예상보다 크므로 절감폭은 §4.3 이 적은 8%보다 커진다.

### 10.5 카드 예산이 두 경로로 갈린 이유 (§9.7 R1 종료)

| 경로 | maxCards / perSystem / perKind | 이유 |
|---|---|---|
| 규칙 기반 (`features/report`) | 64 / 40 / 14 | 토큰을 쓰지 않는다. 좁으면 섹션이 **에러 없이** 사라진다 |
| LLM (`server/src/interpret.ts` `LLM_RETRIEVAL`) | 14 / 7 / 2 | **카드 수 = 원가.** 한 장이 354자이고 그대로 user 턴에 실린다 |

두 경로가 상한을 각자 갖는 것이 맞다 — 같은 값을 쓰면 한쪽은 섹션이 사라지고 다른 쪽은 돈을 태운다.
LLM 쪽 값을 `selectKnowledgeCards` 의 기본값(16/7/2)에 맡기지 않고 서버가 명시하는 이유는,
이 숫자가 바뀌면 README 의 원가표가 같이 틀려지기 때문이다.
