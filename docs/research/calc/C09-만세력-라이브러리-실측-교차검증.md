## 1. 설치 결과

```
$ npm i lunar-javascript korean-lunar-calendar solarlunar
added 3 packages, and audited 4 packages in 2s
found 0 vulnerabilities
```

| 패키지 | import 형태 | 사주 API |
|---|---|---|
| `lunar-javascript` | `const {Solar} = require('lunar-javascript')` | `Solar.fromYmdHms(...).getLunar().getEightChar()` → `getYear/getMonth/getDay/getTime` |
| `korean-lunar-calendar` | `const KLC = require('korean-lunar-calendar')` (생성자 함수, named export 없음) | `new KLC().setSolarDate(y,m,d)` → `getChineseGapja() / getKoreanGapja()` |
| `solarlunar` | `require('solarlunar').default` ← **`.default` 필수** | `solar2lunar(y,m,d)` → `{gzYear, gzMonth, gzDay}` |

⚠️ 세 패키지 모두 **모듈 export 형태가 문서와 다르다.** 첫 시도에서 `cal.getGapJaString is not a function`, `solarlunar.solar2lunar is not a function` 로 전부 실패했다. 실제 prototype 을 덤프해서 확인해야 했다.

⚠️ `lunar-javascript` 의 절기 테이블 키는 **간체자**다 (`惊蛰`, `谷雨`, `处暑`, `小满`, `芒种`). 번체/한국 한자(`驚蟄`, `穀雨`, `處暑`)로 조회하면 **조용히 `undefined`** 를 반환한다 — 예외가 아니라 무응답이라 놓치기 쉽다. 실제로 1차 실행에서 24절기 중 5개가 표에서 누락됐다.

⚠️ `getJieQiTable()` 은 키가 **31개**다 (24절기 + `DA_XUE`,`DONG_ZHI`,`XIAO_HAN`,`DA_HAN`,`LI_CHUN`,`YU_SHUI`,`JING_ZHE` 로마자 키로 이듬해 절기 중복 수록). 또한 기준 날짜가 속한 **음력년** 기준이라, 6월 기준으로 뽑으면 `冬至` 가 **전년도 값**(2024-12-21)으로 나온다.

## 3. 발견 ①: lunar-javascript 의 절기는 **중국 표준시(UTC+8)**

C02 문서가 확보한 KASI 공표값과 대조:

| 연도 | KASI 공표 입춘 (KST) | lunar-javascript 출력 | 차이 |
|---|---|---|---|
| 2024 | 2024-02-04 **17:27** | 2024-02-04 **16:27:07** | **−60분** |
| 2025 | 2025-02-03 **23:10** | 2025-02-03 **22:10:28** | **−60분** |
| 2026 | 2026-02-04 **05:02** | 2026-02-04 **04:02:08** | **−60분** |

전 12절(節) 2년치를 뽑아도 예외 없이 정확히 1시간 차이다. 즉 lunar-javascript 는 **동경 120° 기준**으로 절기를 산출하며, KST 벽시계를 그대로 넣으면 절입 판정이 1시간 앞당겨진다.

### 분 단위 경계 스캔 (실제 출력)

```
## 6. 입춘 경계 분단위 스캔 (2024-02-04, 연주가 바뀌는 정확한 분)
  -> 연주 전환: 16:28 에서 癸卯 → 甲辰
(2024 입춘 KASI 공표: 2월 4일 17시 27분 KST)
```

**2024-02-04 16:28 ~ 17:27 KST 사이에 태어난 사람은 연주가 통째로 틀린다.** 연주가 틀리면 → 월주 오호둔 → 십신 → 대운 방향(연간 음양) → 신살(연지 기준) → 사실상 리포트 전체가 무효다.

### 영향 범위 정량화 (실제 출력)

```
## B. 나이브 사용(KST 벽시계를 그대로 투입) 시 월주 오류율
잘못된 월주가 나오는 창(window): 절입마다 60분 × 12절 × 2년 = 1440분 중 1416분이 실제로 오판
→ 연간 오류 노출: 12절 × 60분 = 720분 / 525960분 = 0.137% 의 출생시각
→ 입춘 1시간 구간은 연주까지 틀림 (60분 / 525960분 = 0.0114%)
```

**월주 오류 0.137%** = 유저 10만 명이면 **137명**이 틀린 사주를 받는다. 그중 연주까지 틀리는 사람이 약 11명. 운세 앱에서 "네이버 만세력이랑 다르다"는 CS 클레임을 유발하는 정확히 그 지점이다.

## 4. 발견 ②: "입력을 −1시간 시프트" 우회책은 틀린다

가장 먼저 떠오르는 우회책(KST→CST 변환해서 투입)을 실제로 돌려봤다.

```
## C. "입력을 −1시간 시프트" 우회책이 왜 틀리는가
입력: 2024-02-04 17:00 KST (KASI 입춘 17:27 → 아직 癸卯년 丑월이어야 함)
  나이브 투입 : 甲辰 丙寅 戊戌 辛酉   ← 연주/월주 오답
  −1h 시프트  : 癸卯 乙丑 戊戌 庚申   ← 연주/월주는 정답이나 시주가 酉→申 로 오염
  정답        : 癸卯 乙丑 戊戌 辛酉

## D. 시주 오염 발생률 (−1h 시프트 시)
(참고: 단순 h-1 산술로는 h=0 구간 60건에서 lunar-javascript가 'wrong hour -1' 예외를 던진다)
−1h 시프트 시 시주가 달라지는 비율: 720/1440 = 50.0%
```

시프트하면 연주·월주는 고쳐지지만 **시주가 50% 확률로 오염**된다(시진 2시간 폭의 절반). 게다가 자정 구간에서는 `Error: wrong hour -1` 로 **크래시**한다.

→ **확정 아키텍처**: 연주·월주는 자체 KASI 절기표로 판정, 일주·시주는 원본 KST 시각으로 산출. 하나의 라이브러리에 전부 위임하는 구조는 불가능하다.

## 5. 발견 ③: korean-lunar-calendar 의 간지는 사주 간지가 아니다

TC02/TC03 을 보라. **입춘 직전(17:00)과 직후(18:00) 모두 `癸卯年 乙丑月`** 로 동일하다. 즉 이 라이브러리는 절기를 아예 보지 않고 **음력 월** 기준으로 간지를 매긴다.

추가 불일치:
- TC05 (1988-05-08): `丙辰月` vs 다른 구현 `丁巳月` — 입하(5/5) 이후인데 음력 3월이라 辰월로 판정
- TC08 (1960-01-01): `丁丑月` vs `丙子月`
- TC13 / TC14 / TC15 도 월주 불일치

**월주가 다른 구현과 6/15 케이스에서 불일치.** 이 패키지는 양·음력 변환 전용이다. 사주 월주에 쓰면 안 된다. (일주 간지는 정확히 일치하므로 일주 크로스체크용으로는 유효하다.)

## 6. 발견 ④: solarlunar 는 절기 판정이 날짜 단위

lunar-javascript(sect2) 와 3주 비교 결과 **1/15 불일치**:

```
## 3. lunar-javascript vs solarlunar 3주(년월일) 불일치
- TC13: lunar-js=[庚戌 壬午 戊子] solarlunar=[庚戌 癸未 戊子]
불일치 1/15
```

TC13 은 **1970-07-07 09:00**, 소서 절입 당일이다. 소서는 그날 늦은 시각에 들어오므로 09:00 은 아직 **午월**이 맞다. solarlunar 는 `getTerm(y, n)` 이 **일(day)만 반환**하고 시·분을 갖지 않아, 절입 당일이면 시각과 무관하게 다음 달로 넘겨버린다.

→ **절입 당일 출생자(연 12일, 약 3.3%)** 의 월주가 최대 24시간 폭으로 틀릴 수 있다. 0.137% 짜리 lunar-javascript 문제보다 24배 큰 오류다.

## 7. 발견 ⑤: 야자시(sect) 처리 — 4/15 케이스에서 일주가 갈림

```
## 2. 야자시 처리(sect1 vs sect2) 불일치
- TC01 야자시 경계 23:30: sect1 일주=辛未 / sect2 일주=庚午
- TC07 입춘 직전 + 야자시: sect1 일주=甲戌 / sect2 일주=癸酉
- TC10 2025 입춘 직후 + 야자시: sect1 일주=甲辰 / sect2 일주=癸卯
- TC12 연말 야자시: sect1 일주=丙辰 / sect2 일주=乙卯
```

`EightChar.setSect(1|2)` 로 전환된다.

| sect | 23:00~23:59 처리 | 결과 |
|---|---|---|
| 1 | 일주를 **익일**로 넘김 (자초환일) | 辛未 |
| 2 | 일주 **당일 유지**, 시주만 子 | 庚午 |

C03 문서가 확정한 한국 주류 규칙은 **(a) 당일 유지 = `sect=2`**. `korean-lunar-calendar`·`solarlunar` 도 날짜 기반이라 sect=2 와 같은 결과를 낸다.

⚠️ **일간이 바뀌면 십신 전체가 뒤집힌다.** TC01 은 庚 ↔ 辛 로 갈리는데, 이건 일간 자체가 달라지는 것이라 비겁/식상/재성/관성/인성 배치가 전부 재계산된다. 반드시 명시적으로 `setSect(2)` 를 호출해야 한다 — 기본값에 의존하지 말 것.

23시대 출생은 전체의 **1/24 ≈ 4.2%**. 야자시 규칙 선택은 절기 버그보다 **30배 많은 사용자**에게 영향을 준다.

## 9. 아키텍처 (1차안 — §11.6에서 대체됨)

> ⚠️ 아래는 `manseryeok` 을 모르던 시점의 1차안이다. **§11.6이 최종안**이다. 자체 천문 구현은 불필요한 것으로 판명됐다. 이력 보존을 위해 남긴다.

```
입력: 생년월일시(KST 벽시계) + 성별 + 출생지
  │
  ├─[1] 시각 정규화 (C01)
  │     한국 표준시 이력(1954~1961 UTC+8:30) + 서머타임 구간 → 절대시각(UTC)
  │     ※ 어떤 라이브러리도 해주지 않음. 자체 구현 필수.
  │
  ├─[2] 연주·월주  ← 자체 구현
  │     KASI 절기표(KST, 초 단위) 이진탐색 → 직전 節 → 월지
  │     입춘 기준 연 판정 → 연간, 오호둔 → 월간
  │     ※ lunar-javascript 사용 금지 (§3)
  │
  ├─[3] 일주  ← lunar-javascript (setSect(2)) 또는 자체 JDN 공식
  │     4개 구현 전부 일치하므로 안전. 자체 구현 시 크로스체크용으로 활용.
  │
  └─[4] 시주  ← 원본 KST 시각(+ 진태양시 옵션) 기준, 오서둔
        ※ 절대로 시프트된 시각을 쓰지 말 것 (§4, 50% 오염)
```

**lunar-javascript 는 "일주 계산기 + 크로스체크 오라클"로만 쓴다.** 절기·시각 보정은 전부 자체 구현.

## 11. 2차 실측 — `manseryeok` 패키지 (§0·§9 결론을 뒤집음)

1차 bake-off에서 이 패키지를 누락했다. 1차 워크플로우의 갭 크리틱이 **문서 04 vs 문서 11 정면 모순**(만세력 라이브러리 연도 상한이 2050인가 2300인가)을 지적해 재조사한 결과 발견했다.

### 11.1 패키지 식별 — 동명이인 주의

```
$ npm view manseryeok version license description repository.url
version = '2.0.0'
license = 'MIT'
description = 'Korean Saju (Four Pillars) and Manseryeok calculation library with true solar time correction'
repository.url = 'git+https://github.com/yhj1024/manseryeok.git'

$ npm view @fullstackfamily/manseryeok version license
version = '1.0.8'
license = 'MIT'
```

**`manseryeok` (yhj1024) 와 `@fullstackfamily/manseryeok` (urstory) 는 서로 다른 패키지다.** 문서 11은 후자만 보고 "연도 상한 2050"을 최상위 리스크(R1)로 올렸는데, 전자는 전혀 다른 커버리지를 갖는다. **문서 11의 R1과 그에 딸린 "천문 알고리즘 자체 구현" 액션은 무효다.**

### 11.2 절기 정확도 — KASI 완전 일치 (실제 출력)

```
--- 입춘 (KASI: 2024=17:27, 2025=23:10, 2026=05:02 KST) ---
2024 | {"index":2,"name":"입춘","hanja":"立春","date":"2024-02-04T08:27:00.000Z"}
   UTC: 2024-02-04T08:27:00.000Z | KST: 2024-02-04 17:27:00
2025 | {"index":2,"name":"입춘","hanja":"立春","date":"2025-02-03T14:10:00.000Z"}
   UTC: 2025-02-03T14:10:00.000Z | KST: 2025-02-03 23:10:00
2026 | {"index":2,"name":"입춘","hanja":"立春","date":"2026-02-03T20:02:00.000Z"}
   UTC: 2026-02-03T20:02:00.000Z | KST: 2026-02-04 05:02:00
```

| 연도 | manseryeok (KST) | KASI 공표 | lunar-javascript | 판정 |
|---|---|---|---|---|
| 2024 | 2024-02-04 17:27:00 | **17:27** | 16:27:07 (−60분) | manseryeok ✅ |
| 2025 | 2025-02-03 23:10:00 | **23:10** | 22:10:28 (−60분) | manseryeok ✅ |
| 2026 | 2026-02-04 05:02:00 | **05:02** | 04:02:08 (−60분) | manseryeok ✅ |

**§3에서 지적한 UTC+8 문제가 없다.** 반환값이 UTC 기반 `Date` (ISO 문자열)라 시간대 해석의 여지 자체가 없다. 분 단위로 절사되어 있어 KASI 공표 형식(분)과 그대로 대응한다.

### 11.3 사주 4기둥 — 경계 케이스 전부 정답 (실제 출력)

```
DEFAULT_LONGITUDE = 127.5
TC02 | 입춘(17:27) 직전  → 계묘연주, 을축월주, 무술일주, 신유시주   ✅ 정답
TC03 | 입춘 직후        → 갑진연주, 병인월주, 무술일주, 신유시주   ✅ 정답
TC13 | 소서 당일 09:00  → 경술연주, 임오월주, 무자일주, 정사시주   ✅ 정답(午월 유지)
TC01 | 1990-05-05 23:30 → 경오연주, 경진월주, 경오일주, 병자시주
TC10 | 2025-02-03 23:20 → 을사연주, 무인월주, 계묘일주, 임자시주
```

- **TC02/TC03**: lunar-javascript 가 틀리는 바로 그 케이스(§3)를 정확히 갈라낸다.
- **TC13**: solarlunar 가 틀리는 절입 당일 케이스(§6)도 정확하다.

**야자시 시주에서 lunar-javascript 와 갈린다 — 그리고 manseryeok 이 맞다:**

| 케이스 | 일주 | manseryeok 시주 | lunar-javascript(sect2) 시주 | 오서둔 정답 |
|---|---|---|---|---|
| TC01 | 庚午 (庚일) | **丙子** | 戊子 | 庚일 자시 = **丙子** ✅ manseryeok |
| TC10 | 癸卯 (癸일) | **壬子** | 甲子 | 癸일 자시 = **壬子** ✅ manseryeok |

lunar-javascript 는 `sect=2` 에서 **일주는 당일로 유지하면서 시간(時干)만 익일 일간으로 遁**한다 — C03 문서가 분류한 유파 **(c) yajasi-nextstem** 이다. 즉 자기 자신이 낸 일주(庚午)와 시주(戊子)가 오서둔상 **서로 모순**된다. manseryeok 은 일관되게 유파 **(a) 당일 유지** 이며, 이것이 C03이 확정한 한국 주류 규칙이다.

→ 23시대 출생은 전체의 **4.2%**. lunar-javascript 를 시주에 쓰면 이 4.2% 전원의 시간(時干)이 틀린다.

### 11.4 연도 커버리지 — 문서 04·11 둘 다 부정확

```
LUNAR_MIN_YEAR: 1391   LUNAR_MAX_YEAR: 2100
--- getSolarTermsOfYear ---
1800 OK, terms = 24 / 1900 OK / 2100 OK / 2200 OK / 2300 OK
```

| 기능 | 실측 범위 | 문서 04 주장 | 문서 11 주장 |
|---|---|---|---|
| 절기 계산 | **1800~2300 이상** (천문 계산이라 사실상 무제한) | 1800~2300 ✅ | 2050 상한 ❌ |
| 음↔양력 변환 | **1391~2100** | 1800~2300 ❌ | 2050 상한 ❌ |

- 사주 계산은 절기만 쓰므로 **연도 상한은 실무상 문제 없음**.
- 음력 생일 입력 지원은 **2100년 상한** — 현재 서비스에 무관.
- **문서 11의 R1(최상위 리스크)은 폐기. 문서 04의 "음양력 1800~2300" 서술도 정정 필요.**

### 11.5 남은 확인 사항

- `DEFAULT_LONGITUDE = 127.5` — 문서 03(126.978°/−32분)과 **다른 상수**다. 갭 크리틱이 지적한 "진태양시 상수 3종 불일치"의 실체. 단 TC02(17:00 → 辛酉시)를 보면 **기본값에서는 경도 보정이 시주에 적용되지 않은 것으로 보인다**(보정 시 16:30 → 申시가 되어야 함). 옵션 인자 확인 필요. `[미검증]`
- 한국 표준시 이력(1954~1961 UTC+8:30)·서머타임 자동 처리 여부 미확인. **처리하지 않을 가능성이 높으며, 그렇다면 자체 전처리 필수.** `[미검증]`
- `getLuckPillars`(대운), `getTenGodChart`(십신), `getVoidBranches`(공망) 의 유파 선택이 C04~C06 확정안과 일치하는지 미대조. `[미검증]`
- 라이선스 MIT 확인 완료. 번들 크기·최근 커밋일 미확인. `[미검증]`

### 11.6 수정된 아키텍처

```
[1] 시각 정규화   ← 자체 구현 (표준시 이력 + 서머타임 + 진태양시 정책)
[2] 연주·월주    ← manseryeok.calculateFourPillars  (절기 KASI 일치)
[3] 일주         ← manseryeok  (lunar-javascript 로 100년치 전수 크로스체크)
[4] 시주         ← manseryeok  (야자시 유파 (a) 일치)
[5] 십신/대운/공망 ← manseryeok 후보, 단 C04~C06 확정 유파와 대조 후 결정
```

**자체 천문 계산 구현은 불필요하다.** C11 프로토타입의 목적은 "대체 구현"이 아니라 **manseryeok 검증용 독립 오라클** 로 재정의한다.

## 12. 남은 검증 (미완)

세션 토큰 한도로 중단됨. 재개 시 수행 (**우선순위 순**):

1. **manseryeok 옵션 전수 확인** — `calculateFourPillars` 의 경도/진태양시/야자시 옵션 인자, 한국 표준시 이력·서머타임 처리 여부. 소스(`node_modules/manseryeok/dist/`)를 직접 읽어라. §11.5의 `[미검증]` 3건 해소가 최우선이다.
2. **manseryeok 의 십신·대운·공망 유파 대조** — `getTenGodChart` / `getLuckPillars` / `getVoidBranches` 결과가 C04·C05·C06 확정안과 일치하는지. 불일치하면 해당 기능만 자체 구현.
3. C10 골든 테스트셋 30건 구축 → manseryeok 로 전수 검증
4. C11 독립 오라클 구현 → manseryeok 과 일주 100년치·절기 2020~2030 전수 대조
5. `sxtwl`(pip) 설치해 절기 시각 3자 대조(manseryeok vs sxtwl vs KASI)
6. 각 패키지 `npm view <pkg> time.modified dist.unpackedSize` 로 번들 크기·유지보수 상태 확인
7. 온라인 만세력(네이버·점신·포스텔러)과 15케이스 대조 — 자동화 불가 시 수동 표본
