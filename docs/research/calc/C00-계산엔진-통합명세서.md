# C00 — 계산 엔진 통합 명세서 (Single Source of Truth)

> **문서 지위**: C01~C17 전 조사문서의 **확정 결론만** 모은 구현 규격서. 조사 근거·실측 로그·부결된 대안은 각 원 문서에 있고, 여기에는 **"무엇을 어떻게 구현하는가"** 만 적는다.
> 원 문서와 본 문서가 충돌하면 **본 문서가 이긴다**. 원 문서를 고칠 때는 본 문서의 해당 행도 함께 고친다.
>
> **엔진 버전**: `SAJU-ENGINE-1.0.0`
> **작성 기준일**: 2026-08-11
> **선행 문서**: C01(시각정규화) C02(절기) C03(4기둥) C04(십신·신살) C05(신강신약·용신) C06(대운) C07(별자리) C08(통합점수) C09(라이브러리 실측) C10(골든셋) C11(독립오라클) C12(manseryeok 감사) C13(구현체 교차감사) C14(KASI 절기데이터) C15(표준시 확정검증) C16(룩업 1차사료검증) C17(신강신약 계수) **C19(별자리 실측검증 — §G/§H9/§S7-3 정정 반영)** **C22(M0 골든셋 수정·프로덕션 골든셋·회귀 하네스 — §5.2/§6.1/§6.2/§6.3/§4.3/§8 정정 반영)**
> **데이터 자산**: `tables.json`(44표) `strength-params.json` `golden-set.json`(축① 287건) **`golden-set-prod.json`(축② 321건 + 재수집대기 80건)** `golden-solarterms.json`(552건) `proto/solarterms-de440s.json`(7,080건) `proto/ref.mjs`(레퍼런스 구현, F3·GAP 정정본) `proto/gen-prod.mjs`(축② 생성기)

## 0. 최상위 확정 사항 (이것만 어기지 않으면 나머지는 세부사항)

| # | 확정 |
|---|---|
| **F1** | 만세력 라이브러리에 계산을 위임하지 않는다. `manseryeok` / `lunar-javascript` / `sxtwl` 은 **CI 회귀 오라클 전용**이며 프로덕션 번들에 포함하지 않는다. (C13: manseryeok 절기는 lunar-javascript 파생물 → 상호 크로스체크가 순환 검증) |
| **F2** | 절기는 **빌드타임에 Skyfield + JPL DE440s 로 생성한 초(秒) 정밀 사전계산 테이블**을 쓴다. 런타임 천문계산 없음. astronomy-engine 은 오라클로도 부적합(DE440s 대비 max 175.31초). |
| **F3** | 절기 판정(연주·월주)은 **UTC 절대순간** 비교다. 진태양시·표준시·야자시 옵션의 영향을 받지 않는다. |
| **F4** | 시각 정규화(표준시 이력·서머타임·경도·균시차)는 **100% 자체 구현**한다. `KR_TIMELINE` 하드코딩(29세그먼트)을 쓰고 런타임 `Intl`/ICU 에 의존하지 않는다. (C15: 142,988 표본 대조 불일치 0) |
| **F5** | 일주(日柱)는 `(JDN_정오 − 11) mod 60`. 1582-10-15 이전은 **율리우스력 JDN** 분기. (C11: proleptic 그레고리를 쓰면 1391년이 8칸 어긋남) |
| **F6** | 모든 계수·임계값은 `strength-params.json` / `tables.json` 에서만 읽는다. **코드에 숫자 리터럴 금지.** |
| **F7** | 엔진은 순수함수다. `Date.now()` `Math.random()` `Intl` `toLocaleString()` 어느 것도 계산 경로에 등장하지 않는다. |
| **F8** | 유파 분기는 **사용자 설정으로 노출하지 않는다**(§3의 노출여부 열 참조). 결과가 갈리는 창(window)에 들어가면 **경고 배지**를 띄운다. |
| **F9** | 지원 범위: 양력 **1900-01-01 ~ 2100-12-31** 출생. 밖은 계산하지 않고 `OUT_OF_RANGE` 로 거부한다. 절기 테이블은 **1850~2149**(DE440s 커버리지 상한 2150-01-22 때문에 2150년은 소한·대한 2건만 생성 가능 → 잘라낸다). **2100년생의 세운은 2200년까지 필요하지만 2150 이후 입춘 절입 시각은 테이블에 없다** → §S6-4(a-2) 의 강등 경로(간지 산술 + 경계 미표기 + 경고)를 따른다. `OUT_OF_RANGE` throw 금지. |
| **F10** | 회귀 기준은 **두 축으로 분리한다**. ① **레퍼런스 회귀**: `golden-set.json` 287건을 *각 케이스에 기록된 규약*(`tzMode`/`longitude`/`jasiRule`/`region`/`stdOffsetMinutes`+`dstMinutes`)으로 재현 — **280/280 (4기둥) · 280/280 (십신) · 275/275 (대운)**. ② **프로덕션 회귀**: 확정 유파(historical TZ + TRUE_SOLAR + yajasi + 출생지 경도)로 재생성한 `golden-set-prod.json` — **M0 에서 생성 완료, 실측 321/321**(4기둥·십신·대운·교운±60초). **①의 수치를 프로덕션 엔진의 머지 게이트로 쓰면 안 된다**(현 골든셋 287건 중 273건이 `raw_kst`+`longitude:null`, 16건이 비-yajasi 이라 확정 유파로는 실측 **172/280 = 61.43%** — F3 정정 전에는 160/280 = 57.14% — 밖에 통과하지 못한다, §6.3). **②는 외부 정답이 아니라 락파일**이므로 정확도 근거로 인용 금지. |

  };
  corrections: {
    stdOffsetMinutes: number;         // 540 / 510 / 507.8667 …
    standardMeridianDeg: number;      // stdOffsetMinutes / 4
    dstMinutes: number;               // 0 | 60
    longitudeMinutes: number;         // 4 × (λ − λ_std)
    eotMinutes: number;               // 균시차
    totalMinutes: number;             // −dst + L + E (벽시계 기준 총이동)
    eotAlgorithm: EotAlgorithm;
    mode: TrueSolarMode;
  };
  flags: TimeFlags;
  notes: string[];                    // 사용자 노출용 경고 문구 키

## 2. 단계별 확정 알고리즘

각 항목은 **(a) 채택 / (b) 왜 이 선택인가 / (c) 대안과 결과 차이 / (d) 참조** 4단으로 적는다.

### S0. 입력 검증 · 정규화

#### S0-1. 범위 가드
- **(a)** 양력 환산 후 `1900-01-01 ≤ date ≤ 2100-12-31` 밖이면 `EngineError('OUT_OF_RANGE')`. 날짜 유효성은 실제 달력으로 검사(2023-02-29, 1900-02-29, 2024-04-31 전부 거부). `hour ∈ [0,23] 정수`, `minute ∈ [0,59] 정수`.
- **(b)** 절기 테이블 정밀 구간(**1850~2149**)의 안쪽 여유. DE440s 커버리지는 1849-12-26 ~ **2150-01-22** 라 2150년 이후는 생성 자체가 불가능하다. 2100년생의 대운 100년 전개(세운 2200년까지)는 간지 산술로 계속 표기하되 **2150 이후 세운은 절입 시각을 알 수 없으므로 §S6-4(a-2) 의 강등 규칙**(간지만 표기 + 경계 미표기 + 경고)을 따른다.
- **(c)** manseryeok 은 연도 100~9999 를 통과시키고 보정표 밖(1800 미만 / 2300 초과)에서 **조용히 틀린 값**을 낸다(1750년 −6.56분, 1799년 −7.52분, 2350년 +7.05분, 2500년 +11.85분). 우리는 예외를 던진다.
- **(d)** C12 §확정범위, C13 §유효범위, C10 §DE440s 커버리지

#### S0-2. 음력 → 양력 변환
- **(a)** 빌드타임에 추출한 **음력 테이블**(1900~2100, 월 대소·윤달 비트필드)로 변환한다. 런타임 라이브러리 의존 없음. 결과는 `NormalizedInput.solar`, 원본은 `lunarSource` 에 보존. **캐시 키에는 양력만 들어간다.**
- **(b)** 음력 입력자와 같은 양력일의 양력 입력자는 같은 사주이므로 캐시 키가 같아야 한다.
- **(c)** `korean-lunar-calendar` 는 간지를 **음력 월 기준**으로 매겨 절기 기준 사주와 체계가 다르다(월주 6/15 케이스 불일치). manseryeok `lunarToSolar` 는 1391~2100 왕복 2,130건 무결이지만 F1 에 따라 테이블만 추출한다.
- **(d)** C09 §5, C12 §음양력변환

#### S0-3. 출생지 좌표
- **(a)** `regionCode` → 좌표 룩업(시/군/구, OSM Nominatim 시청 좌표 기준). 미선택 시 기본값 **서울시청 λ=126.9784204, φ=37.5665**. 좌표는 소수 4자리 반올림 후 캐시 키에 넣는다.

### S1. 시각 정규화

#### S1-1. 확정 공식 (순서 고정)
```
(1) UTC        = W − (O_std + O_dst)          ← 갭/오버랩 판정도 여기서
(2) λ_std      = O_std / 4
(3) L          = 4 × (λ − λ_std)              [분]
(4) E          = EoT(UTC)                     [분]   ← UTC 기준 JD 로 계산
(5) apparentMs = UTC + (O_std + L + E) × 60000   ← 진태양시 (절대순간 기반)
                = UTC + (4λ + E) × 60000         ← 동치. 4λ_std = O_std 이므로 4λ = O_std + L
(6) effectiveWall = UTC + (O_std + O_dst)     ← 실제 시계 판독값 (갭 보정 반영)
```
- **(a)** 위 6줄. **`T = W − O_dst + L + E` 형태의 벽시계 항등식을 코드에 쓰지 않는다.**
- **(a-2)** **(5)(6) 은 둘 다 「epoch ms 에 오프셋 분을 더한 뒤 UTC 필드로 분해하면 해당 로컬 시각이 나온다」는 규약이다.** (5) 에 `O_std` 가 빠지면 결과가 9시간(현대 한국) 어긋난다 — 서울 2024-06-15 09:00 KST 를 `UTC+(L+E)` 로 계산하면 2024-06-14T23:27:23 (일주 己酉·시주 甲子)이 나오지만 정답은 2024-06-15T08:27:23 (일주 庚戌·시주 庚辰)이다. **`O_dst` 는 apparent 에 더하지 않는다**(§1.2.3 `corrections.totalMinutes = −dst + L + E` 와 정합).
- **(b)** 갭 구간에서 SHIFT_FORWARD 를 적용하면 실제 판독은 `W+Δ` 가 되므로 벽시계 항등식은 **최대 60분 틀린다**(1988-05-08 02:30: 벽시계 항등식 01:01 vs 정답 02:01). C15 초기 구현에서 실제로 발생한 버그다. **검산**: SHIFT_FORWARD → UTC 1988-05-07T17:30Z, O_std 540, L −32.086, E +3.512 → (5) = 17:30Z + (540 − 28.574)분 = **1988-05-08 02:01:26** ✓ (구식 (5) 는 17:01 을 낸다).
- **(d)** C15 §정정-C01§0.2, C01 §0.2

- **(c)** **C01 §1.2 는 1908 전환을 `15:30Z`, 1954 전환을 `15:30Z` 로 기재했으나 둘 다 오류다.** 정정 결과 1908-04-01 00:00:00~00:02:07 이 **갭**이 되고(C01 누락), 1954년 오버랩 창은 `03-21 00:00~00:29` 가 아니라 **`03-20 23:30:00~23:59:59`** 다. 한국어 위키백과는 1954 전환을 `03-21 00:30`(=15:30Z)로 적어 tzdb 와 **30분 어긋나며** 대통령령 제876호 원문 미확보로 미해결 — **tzdb 채택**(모든 OS/런타임이 tzdb 를 쓰므로 재현 가능).

#### S1-4. 갭 / 오버랩 정책

### S3. 네 기둥

#### S3-1. 연주
```

#### S3-2. 월주 — 오호둔(五虎遁)
```
OHODUN[g]   = (2g + 2) mod 10                              // 년간 → 寅월 천간

```
- **(c)** **`(2g + 지지index) mod 10` 식은 코드에서 금지.** 子·丑월(monthOrder 10·11 인데 지지 index 는 0·1)에서 2 어긋난다. 반례: 甲년 子월 = 실제 **丙子**인데 그 식은 甲子를 낸다. 甲년 12개월은 丙寅 丁卯 戊辰 己巳 庚午 辛未 壬申 癸酉 甲戌 乙亥 **丙子** 丁丑.

#### S3-3. 일주
```

### S6. 대운 · 세운 · 월운

#### S6-1. 방향
```
forward = (연간 陽 && 남) || (연간 陰 && 여)     // XNOR
```
- **(b)** 연간은 **입춘으로 확정된 사주년**의 연간이다(달력 연도 아님). 20조합(10천간 × 2성별) 전수 일치. lunar-python `Yun.py` `yang = 0 == getYearGanIndexExact() % 2`.
- **(c)** 성별이 뒤집히면 대운 간지 전체가 반대 방향으로 간다(1990-08-17 10:00 → 남 乙酉 / 여 癸未). 트랜스젠더·논바이너리 대응이 필요하면 **"명리상 성별"을 별도 필드**로 받아야 한다.
- **(d)** C06 §3, C12 §대운방향

#### S6-2. 대운수 · 교운 일시
```
Δ분 = forward ? (nextJie − birthInstant) : (birthInstant − prevJie)      // 초 정밀
정밀(A) : year  = floor(Δ/4320);  Δ −= year*4320       // 3일 = 1년
          month = floor(Δ/360);   Δ −= month*360       // 6시간 = 1개월
          day   = floor(Δ/12);    Δ -= day*12          // 12분 = 1일
          hour  = Δ * 2                                 // 1분 = 2시간
교운절대순간 changeoverUtcMs = birthInstantUtcMs + round(Δ분 × 480) × 60000   ← 정수 산술로 직접 정의
                              (Δ분 × 1440/3 = Δ분 × 480. 3일=1년 환산의 역수)
exact {year,month,day,hour} = 위 (A)식 분해. **표시 전용** — 교운 순간을 만드는 데 쓰지 않는다
대운수   = max(1, round(floor(Δ분/1440) / 3))           // 한국식, 표기 전용
```
- **(a)** 내부는 **정밀 교운 절대순간(`changeoverUtcMs`, 정수 ms)** 을 저장하고 UI 라벨의 정수 대운수만 위 한국식 공식을 쓴다. 상세 화면에는 항상 교운 일시를 병기한다.
- **(a-2)** **`출생일시 + {y,m,d,h}` 형태의 달력 덧셈을 쓰지 않는다.** 「1년」·「1개월」을 달력 단위로 더할지 고정 일수(365/30)로 더할지, 월→일 순서로 더할지 일→월 순서로 더할지가 결과를 크게 가른다. 실측(1950~2000 × 매월 6일자, 3,672건): 달력월 해석과 30일 해석의 교운일 차이가 **1일 초과 2,499건 = 68.1%, 최대 7.00일**(1965-03-11 출생 `{0년 11개월 0일 10시간}` → 1966-02-11 vs 1966-02-04). 순서 의존도 별도로 존재한다(2000-01-31T09:00Z + `{0y,1m,3d,8h}` → 월→일 2000-03-05 vs 일→월 2000-03-03, 일주 2칸 차). §5.2 의 「교운 일시 ±1일」 예산으로는 이 오차를 잡을 수 없고 `changeoverUtcMs` 가 캐시 대상 출력이므로 D1(결정론)도 함께 깨진다. → **정수 산술 정의를 규범으로 삼고, `exact` 는 `changeoverUtcMs` 에서 역산해 표기만 한다.**
- **(b)** `max(1, round(floor(Δ일)/3))` 은 골든셋 **275/275 = 100%** 를 통과하는 유일한 식이다. `floor` 선적용이 핵심이고, 클램프가 없으면 275건 중 216건(78.5%)만 맞는다(Δ<3일 케이스 **59건**이 0 vs 기대 1). "정수일수 ÷ 3, 나머지 1 버림 / 2 올림"과 수학적 동치임을 확인했다.
- **(c)** 4방식 차이 — **2000-01-01 12:00 여**(己卯년 음녀 순행, 소한 2000-01-06T10:00:40.862 KST 까지 4.9171일): **한국식 1 / 반올림 2 / 버림 1 / 정밀 1년 7개월 20일**. 같은 날 00:00~09:00 출생은 Δ 5.0421~5.4171일이라 **한국식·반올림은 2, 버림은 1**(버림이 2가 되려면 Δ ≥ 6일이어야 하는데 그날 어느 시각에도 도달하지 않는다 → **버림 유파는 이 날 하루 종일 1** 이라 오히려 12:00 이후에 한국식과 일치한다). **한국식과 반올림이 그날 12:00 을 경계로 갈린다.** 시진 단위식(lunar-* `sect=1`)은 분 정보를 버려 최대 2시간(= 교운 10일) 오차를 낳는다(케이스 A 3일 차, 케이스 D 4일 차).
- **(c-2)** 표준시 1시간 오차 = **교운일 정확히 5일**(1분 = 2시간 환산). 중국 라이브러리를 KST 보정 없이 쓰면 안 되는 정량 근거다(1990-08-17 10:00 남 → KST 1997-11-30 vs CST 1997-11-25).
- **(c-3)** manseryeok 은 `Math.max(1, Math.round(days/3))` 로 유파 (D) 반올림 고정이며 우리와 갈린다. 또한 클램프 때문에 정밀값 0년0개월0일인 케이스도 1로 표기하는 자기모순이 있다(1980~2020 표본 29,952건 중 **1,476건 = 4.9%** 가 이 클램프에 걸림). 우리는 정밀값을 함께 노출해 모순을 드러내지 않는다.
- **(d)** C06 §4, C10 §대운공식, C11 §정정-골든셋, C12 §대운수

#### S8-3. 정규화 · 가중합 · 분포 보정
```

POP = { saju:(60.268, 8.909), zodiac:(58.655, 27.764),
        mbti:(58.270, 24.178), blood:(70.973, 16.036) }

p        = ecdf(combined)                  // calib.json 101분위 그리드 선형보간
final    = round(interp(ANCHOR, p))
ANCHOR   = [(0,32)(.05,45)(.15,54)(.30,61)(.50,68)(.70,75)(.85,82)(.95,89)(.99,95)(1,99)]
```
- **(a)** 미입력 체계는 가중치를 나머지에 **비례 재분배**한다(혈액형 미입력 → 0.50/0.90, 0.20/0.90, 0.20/0.90).
- **(a-2)** **[C18] `z2p` 는 `sd < 1e-9` 이면 50 을 반환해야 한다.** 혈액형 균등 매트릭스(BL-1) 채택 시 sd=0 이라 미방어 시 `ZeroDivisionError`.

### 5.1 오차 → 결과 변경 확률 변환식

```
절입시각 오차 ε(최대 |오차|, 초) 가 월주를 바꿀 확률
   ≈ 12ε / 31,556,952 = ε / 2,629,746        (節 경계는 하루 1회가 아니라 節 1개당 1회)
절입시각 오차 ε 가 대운수를 바꿀 확률
   ≈ ε / 259,200                              (Δ 축에서 3일마다 1개의 임계 정수일)
```

1. **절입 ±5초 → 월주 오판 0.00019%.** 100만 명 중 2명. 정책 선택(야자시 4.17%, 진태양시 2.14%)에 완전히 묻힌다.
2. **절입 ±60초 → 0.00228%.** lunar-javascript 시간대 버그(0.1245%)의 **1/54** 수준이라 「라이브러리 버그와 같은 급」이라는 옛 논거는 성립하지 않는다. 그럼에도 60초를 상한으로 유지하는 이유는 정확도가 아니라 **재현성**이다 — 60초 오차는 KASI/manseryeok 분 양자화(±30초)의 2배이므로 외부 대조 시 어느 쪽이 옳은지 판정할 수 없게 된다.
3. **Meeus 저정밀식(±14.3분)은 불합격.** 다만 근거는 확률이 아니다 — 월주 오판은 **0.0327%** 로 절대값이 작지만, 1900~2100 12절 2,412건 중 9건은 **달력 날짜까지** 뒤집히고(외부 대조·CS 재현이 불가능해진다) 2000~2030 12절 372건 중 355건(95.4%)이 분 단위 불일치, 최대 843.4초로 §5.2 의 S2 게이트(≤5초/≤30초)를 두 자릿수 배율로 초과한다.
4. **분 단위 양자화(현행 만세력 관행)의 실제 비용은 0.0012%.** 즉 "초 정밀"은 정확도보다 **재현성·회귀 안정성** 때문에 채택한다.
5. **정확도 예산의 실질 상한은 천문학이 아니라 유파다.** 리스크 규모 순위:

| 순위 | 원인 | 영향 비율 |
|---|---|---|
| 1 | 야자시 유파 선택 | **4.1667%** |
| 2 | 진태양시 ON/OFF (일주) | **2.1409 ~ 2.2480%** |
| 3 | 서머타임 보정 여부 (해당 코호트 내) | 15.20 ~ 22.82% |
| 4 | 巳 지장간 (신강신약 2치) | 0.518% |
| 5 | lunar-javascript 절기 TZ 버그 | 0.1245% |
| 6 | 절기 분 양자화 | 0.0012% |
| — | 신강신약 임계값 선택 | **26.5 ~ 38.7%** (별도 축) |
| — | 신강신약 월지 가중 2.0→3.0 | 7.800% |

   **정책 선택(1+2 = 6.31%)이 라이브러리 버그(0.1245%)의 46배다.** 라이브러리를 바꿔도 이 6.31%는 해결되지 않는다.
6. **'절입의 정확한 순간'은 세기당 ±25초의 정의 불확실성을 갖는다.** Swiss Ephemeris(IAU1976 계열)와 Skyfield DE440s(IAU2006 계열)의 입춘 편차가 1900 **+44.18초**, 2100 **−25.60초**로 `(t−J2000)`에 비례한다. **1970~2040 밖에서는 "어느 구현이 맞다"를 말할 수 없다** → 5.2 표의 구간별 허용치가 여기서 나온다.

> **⚠️ 「초월함수는 `z2p` 의 `exp` 1곳뿐이라 비트 단위로 같다」는 근거는 성립하지 않는다.** ① 초월함수는 필수 경로 곳곳에 있다 — S1 균시차(`sin/cos/tan`), S7 태양 VSOP87 축약·달 Meeus 47.A/47.B 120항·GAST·`Asc1`(`sin/cos/atan2/asin/pow`). ② ECMA-262 는 `Math.sin/cos/tan/exp/pow` 를 *implementation-approximated* 로 규정해 정확 반올림을 요구하지 않으므로 V8(node·Android WebView)과 JavaScriptCore(iOS WKWebView)의 마지막 ULP 가 다를 수 있다. 실증: **동일 V8 안에서도 `Math.tan(x) !== Math.sin(x)/Math.cos(x)` 가 200,000 표본 중 65,044건**(상대차 최대 3.32e−16). `JSON.stringify` 는 double 을 왕복 정확 문자열로 직렬화하므로 미양자화 실수 필드(`corrections.eotMinutes`, `apparent.*`, `Placement.lon/deg`, `Aspect.orb`, `SI`, `climateIndex`, `strength.scores`)의 1 ULP 차이가 곧바로 해시 불일치 → 릴리스 차단이 상시 발화한다.
> → **해결**: §7.4 의 양자화를 **출력 전체로 확대**하고(각도 1e−6°, 분 1e−4, 점수 1e−3), 결정론 해시의 비교 대상을 전체 JSON 이 아니라 **양자화된 결정 필드**(4기둥·십신·격국·용신·등급·최종점수)로 한정한다. 판정 경계(궁 경계, 절입 비교, 시지 경계)는 **정수 ms / 정수 인덱스**로만 비교한다.

### 7.3 캐시 키 설계

```ts
// 차트 캐시 키 투영 — normalizedInput 전체가 아니라 이 투영만 canonical 화한다
chartKeyInput = { v, solar, wall, timeUnknown, gender, place }
// L1 : 계산 결과 캐시
cacheKey = sha256(`${ENGINE_VERSION}|${canonical(chartKeyInput)}`)
// L1' : 궁합 (mbti/blood 는 여기에만 들어간다)
cacheKey = sha256(`${ENGINE_VERSION}|${canonical({A:{...keyA, mbti, blood}, B:{...keyB, mbti, blood}})}`)
// L2 : LLM 서사 캐시 (구조 동치류로 축약 → 히트율 극대화)
narrativeKey = sha256(canonical({
  dg: sorted([A.dayStem,  B.dayStem]),     // 55
  dz: sorted([A.dayBranch,B.dayBranch]),   // 78
  mbti: sorted([A.mbti, B.mbti]),          // 136
  zk: min(d, 12-d),                        // 7
  blood: sorted([A.blood, B.blood]),       // 10
}))[0..32]                                 // = 40,840,800 키 (§S8-4)
// yz(연지쌍 78) · band(등급 8) 는 넣지 않는다 — 넣으면 2.55e10 키 ≈ 7.6 TB 로 단일 Redis 가정이 붕괴한다
```

**정규화 규칙(캐시 키 생성 전 필수)**
1. 음력 → 양력 변환은 **정규화 이전**에 끝낸다. 키에는 양력만. **`NormalizedInput.lunarSource` 는 표시 전용이므로 `chartKeyInput` 투영에서 제외한다** — `canonical(normalizedInput)` 을 그대로 해싱하면 같은 양력 1990-05-06 을 양력으로 입력한 사람과 음력 1990-04-12 로 입력한 사람의 키가 달라져 이 규칙과 §S0-2(b) 를 타입이 직접 위반한다.
1-2. **`mbti`·`blood` 도 차트 키에서 뺀다.** `SajuChart` 결과와 무관한데 키에 넣으면 동일 사주의 차트 캐시가 최대 **85배**(17×5)로 흩어진다. 궁합 키(L1′)에만 넣는다.
2. 좌표는 소수 **4자리** 반올림(약 11 m). 같은 동네는 같은 키. *(C08 §9.3 의 "경도 소수 2자리"는 약 1.1 km 로 시지 판정에 영향이 없어 보이나, 진태양시가 일주 경계에도 적용되므로 4자리로 강화한다.)*
3. 생시 모름은 `hour=12, timeUnknown=true` — 결정론 유지.
4. MBTI/혈액형 미입력은 `null` + 가중치 비례 재분배.
5. JSON 직렬화는 `sort_keys=true, separators=(",",":")`, 유니코드 이스케이프 금지.
6. **캐시 키에 이름·닉네임·디바이스ID 를 넣지 않는다.**

**버전 정책**: 배점표·앵커·POP 상수·`tables.json`·`strength-params.json` 중 **하나라도 바뀌면 `ENGINE_VERSION` 을 올린다** → 전 캐시 자동 무효화. 버전을 안 올리고 상수를 바꾸면 같은 입력에 다른 점수가 나가 D1(결정론)을 위반한다.

**캐시 규모**: `narrativeKey` 카디널리티 **40,840,800**(위 5축) × 문단 300 B = **12.3 GB**. Zipf 가정 시 hot set 200만 키 ≈ **600 MB** → 단일 Redis 로 충분. **키에 축을 하나라도 추가하면 이 산정이 무너진다**(연지쌍 추가 시 ×78 = 956 GB, 등급까지 추가 시 ×624 = 7.6 TB → 샤딩·TTL 재설계 필요).
