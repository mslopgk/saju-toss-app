## 1. 결론 요약 (Executive Summary)

1. **유입은 "알고리즘 배분"이 아니라 "지표 신고 → 알고리즘 배분"이다.** 토스는 2026년 7월 `핵심 지표` 기능을 출시하며 *"핵심 지표는 노출·추천 및 성과 분석의 기준으로 활용된다"* 고 공식 명시했다. 즉 개발자가 콘솔에 **활성 지표 1개 + 전환 지표 최대 3개**를 등록하면, 토스가 그 지표를 만족하는 유저와 유사한 유저를 찾아 노출한다. **이것이 현재 확인 가능한 유일한 '오가닉 노출 알고리즘 통제 레버'다.**
2. **검색 경로는 좁고, 통제 가능하며, 효과가 실측되어 있다.** 검색 대상 필드는 단 3개 — ① 앱 이름(기본 포함, 공식 확인) ② 앱 정보의 `검색 키워드` ③ **앱 내 기능의 첫 번째 피쳐만**. 그리고 앱 이름 변경만으로 **검색 유입 2.2배**를 낸 실사례가 토스 공식 블로그에 있다(피카).
3. **혜택탭은 무료 경로가 아니다.** 혜택탭 '새로운 서비스 써보고'는 **프로모션의 '혜택탭 노출 여부'를 '예'로 설정한 파트너의 프로모션만** 노출된다. 즉 **비즈월렛에 포인트를 충전(최소 50,000원)해야 진입 가능한 유료 지면**이다.
4. **그 유료 지면은 지금 축소 중이다.** 혜택탭 일 평균 진입 유저는 1월 7만명대 → 5월 3만명대로 5개월간 절반 이하로 감소했고(파트너 실측), 2026-07-31자로 **혜택탭 내 일부 지면이 종료**되어 다수 파트너가 DAU 30~50% 급락을 보고했다(토스 공식 답변으로 확인).
5. **공유 바이럴에는 확정된 구조적 상한 3개가 있다.** ① 네비바 기본 공유는 `contactsViral`과 **완전히 다른 기능**이라 리워드가 붙지 않음(공식 답변) ② **공유받은 유저가 실제 진입했는지 확인하는 API가 존재하지 않음**(공식 답변) → 초대 성공 기반 리워드 설계 자체가 불가 ③ 리워드 ID 기준 1인 1일 1회 제한.
6. **다중 앱 전략(로빈 21개 앱)은 운세 카테고리에서 이미 차단됐다.** AI 사주 / AI 궁합 / AI 점성술을 각각 출시한 1인 개발자가 **'양산형 앱' 정책으로 통합을 강제**당했고, 생년월일 운세 앱 보유자가 타로 앱 등록 시 *"동일 워크스페이스 내 유사한 서비스/앱 이름/앱 아이콘으로 출시 어려움"* 사유로 반려됐다. → **우리 앱은 반드시 4개 체계를 담은 단일 앱이어야 한다.**
7. **외부 유입이 과소평가돼 있다.** 랜딩 페이지 제작만으로 유입 8.4배를 낸 실사례가 있고(피카), 토스는 `external_link` / `external_search` / `external_share` / `external__owned_social` 등 **외부 referrer 값을 이미 구분해 제공**하며, 외부 광고 가이드(허용 문구/배지)까지 공식 문서로 배포하고 있다.

### 2.1 콘솔 대시보드가 실제로 보여주는 집계 카테고리 (더 거칠다)

referrer 값은 40개 가까이 되지만, **콘솔 대시보드는 이를 묶어서 보여준다.** 공지 원문(토픽 1236):

- **비게임 앱**: `전체탭, 혜택탭, 미니홈, 푸시/알림, 토스 홈 광고, 검색, 기타`
- 게임 앱: `전체탭, 혜택탭, 게임홈, 푸시/알림, 토스 홈 광고, 검색, 연락처 모듈, 기타`

`guide/analytics/dashboard.md`가 명시한 대시보드 제공 지표: DAU(최근 4주 일단위), OS·토스앱 버전 분포, 성별, 연령(10대~60대 이상), **유입경로**, **유입 경로별 리텐션(재방문율)**, 체류 시간, 엑셀 다운로드, 일/주/월 조회.

> **설계 함의**: `getSchemeUri()` / referrer 파라미터로 **앱 자체에서 40개 세분값을 직접 로깅**해야 한다. 대시보드만 보면 `search`와 `all_tab_reco_organic`이 각각 '검색'/'전체탭'으로 묶여 정밀 최적화가 불가능하다. 운영진 공식 답변(토픽 4277): *"현재 유입 경로 레퍼러의 경우, 세분화되어있지 않고 큰 카테고리로 분류되어있습니다. 캠페인 단위로 추적이 필요하실 경우, 쿼리파라미터를 통한 트래킹 부탁드립니다. 레퍼러와 자체 파라미터를 함께 로깅해주셔도 됩니다."*

## 4. 경로 ①: 검색(`search`) — 가장 통제 가능하고, 유일하게 효과가 실측된 경로

### 4.1 검색 인덱스에 들어가는 필드 (공식 확인)

```
검색 매칭 대상 = 앱 이름            (Dylan 공식: "앱 이름은 기본적으로 포함됩니다")
              + 앱 정보 > 검색 키워드
              + 앱 내 기능(피쳐)의 "첫 번째 항목"만
              — 그 외 필드(부제, 상세 설명, 두 번째 이후 피쳐)는 검색 불가
```
seonjeong 공식 원문: *"앱 정보에 입력한 검색 키워드와 앱 내 기능의 첫번째 피쳐로만 검색이 가능합니다. 다른 피쳐 검색은 내부 준비중에 있습니다."*

### 4.2 실측된 효과 — 앱 이름 변경만으로 검색 유입 2.2배

토스 공식 블로그 `arcoi` 편에 실린 **피카(Peeca)** 사례 원문:
- 앱 이름 변경: `Peeca: 결제 전 5초 검색` → **`Peeca: 내 카드 할인돼?`**
- 결과: **"앱인토스 콘솔에서 검색 유입이 평균 2.2배 늘었어요"**
- 별도로 랜딩 페이지 제작 후: **"랜딩 페이지를 만들기 전보다 약 8.4배 늘었어요"** (검색사이트 + Threads 프로필 링크 등록)
- 플랫폼 전환 효과: **"출시 10일 만에, 구글 스토어·애플 앱스토어 양쪽에서 약 3개월 동안 모은 유입 규모에 도달"**

> **해석**: 기능 설명형 이름 → **유저의 질문문(intent) 형태 이름**으로 바꾼 것이 핵심. 우리 앱은 `사주·MBTI·혈액형·별자리 종합운세` 같은 기능 나열형이 아니라 **유저가 실제로 검색창에 치는 말**을 이름에 넣어야 한다.

### 4.3 표시 길이 제약 (토픽 2285 실측)

| 앱 이름 | 공백 포함 길자수 | 전체탭 표시 |
|---|---|---|
| `AI 프로필 사진` | 9자 | 완전 표시 |
| `러브 애널리틱스` | 8자 | **`러브 애널리…` 로 잘림** |

폭(픽셀) 기준으로 추정되며 토스는 정확한 룰을 공개하지 않았다(Dylan: *"담당 팀에 전달드려보겠습니다"*).
→ **앱 이름 앞 6~7자 안에 핵심 키워드를 배치**해야 한다. 예: `오늘의 사주운세` (7자) 형태.

### 4.4 네이밍-키워드 정합성 심사 (토픽 118)

심사에서 **"키워드들 기반으로 앱 이름을 변경해야 한다"** 는 사유로 운영/테스트 앱이 모두 반려된 사례가 있다.
→ 검색 키워드에 `사주/운세/MBTI/별자리/혈액형/궁합`을 넣으려면 **앱 이름이 그 키워드군을 대표해야** 반려를 피한다.

### 4.5 확인 못 한 것

- **검색 키워드 등록 개수 상한**: 문서에 없음. `guide/marketing.md?ask=` 질의에도 *"'앱 검색 키워드 최대 개수' 제한값은 확인되지 않아…"* → **미확인**
- 검색 키워드 글자수 제한 → **미확인**
- 검색 결과 정렬(랭킹) 기준 → **미확인**. 토픽 1623에서 공식 답변 거부(*"채널톡을 통해 부탁드립니다"*)
- 등록 위치는 확인됨: **콘솔 → 워크스페이스 → 앱 → '앱 정보 입력하기' → [수정하기]**. 2026-05-14 업데이트로 **최초 등록 3필드(앱 이름 / appName(수정 불가 고유 ID) / 앱 유형)에서 검색 키워드·카테고리가 제외**되어, 출시 전 단계에서 별도 입력한다.

### 5.2 노출 알고리즘과의 연결 (공식 문구)

> *"토스가 활성 사용자와 비슷한 사용자를 찾아, 우리 앱을 좋아할 만한 사용자에게 노출하고 추천해요."*
> *"핵심 지표를 잘 설정할수록 더 적합한 사용자에게 노출될 기회가 커져요."*
> *"핵심 지표는 노출·추천 및 성과 분석의 기준으로 활용되므로 신중하게 설정해 주세요."*

### 5.3 우리 앱에 대한 직접적 함의

운세 앱의 자연스러운 사용 리듬은 **"매일 아침 1회, 30초~2분"** 이다. 이는 기본 활성 지표와 충돌한다.

| 후보 활성 지표 | 우리 앱 적합성 | 판단 |
|---|---|---|
| 비게임 기본값: **7일 후 재방문** | 운세는 일간 콘텐츠 → 7일 후 재방문율은 오히려 **과소평가**되기 쉬움 | 부적합 가능성 |
| **n일 이후 재방문 (2일)** | "오늘의 운세를 이틀 연속 본 유저" = 진짜 코어. 최소값 2일 사용 가능 | **1순위 후보** |
| n분 이상 체류 (2분) | 사주 풀이/궁합처럼 **읽는 분량이 긴 콘텐츠**를 만들면 달성 가능 | 2순위(콘텐츠 길이 설계와 연동) |
| 하루 n회 이상 방문 (2회) | 운세는 하루 1회가 자연스러움 → 달성률 낮음 | 부적합 |

전환 지표 3칸 배정안(v1): ① **알림 받기 동의한 유저** (리텐션·스마트발송 자격의 선행 조건) ② **인앱 광고 시청 유저**(BM) ③ 커스텀 — `궁합 결과 조회 완료` 또는 `4개 체계 통합 리포트 열람 완료`.

> **이것이 v1에서 반드시 해야 할 단 하나의 '알고리즘 통제' 작업이다.** 비용 0원, 콘솔 설정 + 이벤트 로깅만 필요. 단 **익일 반영**이므로 출시 전에 미리 설정해야 한다.

### 5.4 확인 못 한 것

- `all_tab_reco_organic` / `miniapphome` **노출 선정 기준·슬롯 수·갱신 주기** → **미확인** (토픽 1623 공식 답변 거부, 토픽 2644 무응답)

> **"프로모션의 '혜택탭 노출 여부'를 설정한 파트너사의 프로모션이 노출되고 있어요."**
> *"혜택탭에 노출하면 폭발적인 트래픽을 경험할 수 있어요"*
> *"기존에는 혜택탭에서 프로모션을 누르면 더 이상 볼 수 없었는데, 이제는 계속 볼 수 있어요"*

즉 **등재 절차 = 프로모션 등록 + `혜택탭 노출 여부 = 예`** 이며, 별도 신청서/심사 라인은 존재하지 않는다.

## 7. 경로 ④: 공유 바이럴 — 구조적 상한 3중 확정

### 7.1 두 개의 서로 다른 '공유'를 혼동하지 말 것

| 구분 | 네비게이션 바 기본 공유 | 자체 공유 버튼 (`contactsViral`) | `getTossShareLink` 딥링크 |
|---|---|---|---|
| 트리거 | 상단 네비바 ⋯ | 앱 내 커스텀 버튼 | 앱 내 커스텀 버튼 |
| 리워드 지급 | **불가** (공식: *"상단 네비게이션의 공유 기능과는 다른 점 참고 부탁드립니다"*) | **가능** | 불가 |
| 전달 채널 | 토스 내부 공유 시트 | **토스 알림 푸시**(공식: *"공유는 토스 알림 푸시로 진행돼요"*) | 외부 메신저/SNS (URL) |
| 커스텀 OG 이미지 | **적용 불가** (문서 12 발견) | 해당 없음(푸시 문구는 게임/비게임별 고정) | **`ogImageUrl` 파라미터로 적용 가능** |
| 앱 미설치자 | — | — | **iOS→앱스토어 / Android→플레이스토어** |

### 7.2 `getTossShareLink` 확정 스펙 (공식 문서 원문)

```typescript
function getTossShareLink(url: string, ogImageUrl?: string): Promise<string>;
```
- `url` (필수): **`intoss://` 로 시작**해야 함. 예 `intoss://<앱이름>` / `intoss://<앱이름>/about?name=test`
- `ogImageUrl` (선택): **`https://` 절대 경로 필수**. SNS·메신저 외부 플랫폼 미리보기 이미지
- 반환: `deep_link_value`가 포함된 토스 공유 링크
- **권장 OG 이미지 규격: 1200 × 600 px** (`guide/marketing/open-graph.md`)
- 주의: *"외부 플랫폼은 OG 메타데이터를 캐싱해두기 때문에"* 변경이 즉시 반영되지 않음 → **Kakao Debugger / Facebook Debugger로 캐시 초기화 필요**

### 7.3 `contactsViral` 확정 제약

- **하나의 리워드 ID 기준, 한 사용자에게 하루 한 번만** 공유 리워드 발송 가능 (서로 다른 리워드 ID는 독립)
- **현금성·사행성 보상 등록 불가**
- *"과도한 팝업이나 강제적인 공유 유도는 피해주세요"*
- 알려진 버그/제약: 공유 창을 닫으면 같은 친구에게 재공유 가능(토픽 2768), 친구 목록에 1명만 표시되는 현상(토픽 3414), `sentRewardAmount` 속성명 불일치(토픽 2007), 공유 가능 횟수 제한 기능 부재(토픽 3799)

### 7.4 바이럴 계수(K) 상한 산정

```
K = (공유 버튼 노출 도달률) × (공유 실행률 p) × (1회당 실제 발송 인원 n) × (수신자 진입 전환율 c)
```
확정된 상한 요인:
- `n`: 리워드 ID 1개 기준 **한 수신자당 1일 1회** → 같은 친구에게 반복 발송으로 K를 부풀릴 수 없음
- **`c`를 측정할 방법이 없다.** 공식 답변: *"현재 공유 받은 유저가 공유 링크를 통해 접속 했을때 보상을 줄 수 있는 API 는 없습니다"* → **초대 성공 기반 리워드 = 구현 불가**
- 대안(운영진 제안): **공유 직후 즉시 지급** → 원 질문자가 지적한 대로 **어뷰징에 그대로 노출**
- 인앱 공유 유입이 어떤 referrer로 집계되는지도 **공식 미확인**(토픽 3660, 스태프 무응답). `external_share` 값이 문서에 존재하나 인앱 공유와의 매핑은 미확인

> **결론: 현재 앱인토스에서 "친구 초대 성공 → 보상" 형태의 정통 바이럴 루프는 플랫폼이 지원하지 않는다.** 궁합 기능의 공유는 **"OG 이미지가 붙은 외부 링크(`getTossShareLink`)"** 형태로만 의미가 있으며, 이는 **성과 측정이 자체 쿼리파라미터에 의존**한다.

## 8. 경로 ⑤: 유료 채널 — 스마트 발송 / 토스 홈 광고 / 토스애즈

### 8.1 스마트 발송 (`guide/marketing/smart-message.md` + 실측)

| 항목 | 확인된 값 |
|---|---|
| 발송량 상한 | **워크스페이스(사업자)당 10만 건** |
| 캠페인 목적 | **"신규 유입 유도하기: 미니앱을 아직 써보지 않은 사용자에게 첫 진입을 유도"** / "재방문 유도하기" |
| 타게팅 | **pCTR(예상 클릭률)로 서비스 고관여자 예측**, 클릭이 잘 일어나는 시간대 예측 |
| 심사 | 광고성 메시지 **자동 검수**. 기능성 메시지는 사전 알림 동의 필요 |
| 비용 | **문서에 명시 없음 → 미확인** |
| 신규 미니앱 사용 가능 여부 | 문서 명시 없음. 단 토픽 2614에서 *"DAU가 너무 없어서"* 스마트 푸시를 못 보낸 사례 있음 → **DAU 하한 조건 존재 의심** `[미검증]` |
| 실측 성과 | 초기 3일 약 1만건 → 이후 하루 0~수백건. 3주 총 약 5만건. CTR 4~15%. 기존 푸시 대비 **1/10~1/20 수준 유입** |

**로빈의 실제 전략(토스 공식 블로그 `robin-26-3-13`)** — 문서 07이 "CTR 20%"를 오가닉 노출로 오독했을 가능성이 큰 지점:
- 21개 앱을 7주 만에 출시 (초기 11개 후 마케팅 전략 전환)
- 유저 발견 경로: *"직접 검색하거나 미니앱 홈에서 서비스를 발견"* + **푸시 메시지를 통한 유입이 주요 경로**
- **"스마트발송을 토스 포인트 프로모션과 결합하는 게 가장 효과적"**
- 메시지 카피 실험: *"'날씨를 확인해 보세요'라는 메시지보다 **'날씨를 확인하고 1원 받아요'**가 훨씬 성과가 좋았"*
- 포인트 금액 A/B: **1원~20원** 구간 검증
- **CTR: 초기 4~5% → 날씨 앱 20% 초과** ← **이것은 스마트발송(푸시) CTR이지, 지면 노출 CTR이 아니다**
- 첫 수익 700원 → 배너 광고 추가로 수익 파이프라인화

> **핵심 재해석: 로빈의 "CTR 20%"는 오가닉 디스커버리 성과가 아니라 `스마트발송 + 포인트 1원` 조합의 푸시 CTR이다.** 즉 로빈의 성공 공식 = **유료(포인트) + 발송량**이며, 이는 워크스페이스당 10만건 상한에 걸린다.

### 8.2 토스 홈 광고 = 홈 인텔리 (`home_intelligence`)

- **입점 조건 / 최소 예산 / 과금 방식: 전부 공개 문서에 없음 → 미확인.** 문서 질의 답변: *"입점 조건과 최소 예산은 확인할 수 없습니다 … apps-in-toss 채널톡으로 문의하는 것이 가장 빠릅니다."*
- `guide/marketing.md`의 마케팅 수단 목록(스마트 발송 / 프로모션 / 공유 리워드 / OG 이미지 / 외부 광고 가이드 / 토스애즈 픽셀 연동)에 **토스 홈 광고는 포함되어 있지 않다** → 별도 라인의 상품
- 실측 성과(토픽 841, Albert, 2025-10): 소재 대부분 **하루 1,000회 노출 미만**, CTR 4%+ 소재도 **1주일 약 2,500회**, 동시 노출 배너 2~3개, 신규 승인 소재는 **시간당 약 10회**
- 운영진 대응: *"운영 담당자에게 내용 전달드렸습니다. 내일 채널톡으로 문의 부탁드릴게요"*

> **홈 인텔리는 "최대 트래픽 소스"라는 문서 02의 추정과 달리, 개별 파트너 관점에서는 노출량이 극히 적었던 실측 사례가 존재한다.** 최소 예산·단가는 여전히 미확인.

### 8.3 토스애즈 (`tossads`)

- 미니앱 대상 **최소 집행 금액 / CPI / CPC 벤치마크: 커뮤니티·문서 어디에도 없음 → 미확인**
- 확인된 것: **토스 픽셀 연동**으로 전환 추적 시도 중이나 *"광고 클릭이 있는데 페이지 조회 및 기타 전환이 안잡히는 상황"* 등 **전환 추적 이슈 다수**(토픽 4261, 4268, 4050)
- SSP 정책 개정 공지 존재(토픽 4485)

> **"토스에서 [서비스명] 검색해보세요"가 공식 허용 문구라는 점이 결정적이다.** 외부 콘텐츠 → 토스 검색 → `search` referrer 라는 루프를 토스가 명시적으로 승인하고 있다. 즉 §4의 앱 이름 최적화와 외부 콘텐츠 마케팅은 **곱셈 관계**다.

## 10. 치명적 제약: '양산형 앱' 정책 — 운세 도메인에서 이미 집행됨

| 사례 | 내용 |
|---|---|
| 토픽 2834 (2026-03-08) | 1인 개발자가 **AI 사주 / AI 궁합 / AI 점성술**을 개별 출시 → 토스가 **'양산형 앱' 위반**으로 통합 요구. 개발자는 "학문적 기반과 유저층이 다르다"고 항변했으나 토스는 **"사용자 관점의 유사성"** 을 근거로 관철. 통합 이행 후 1/12에 사전 고지 없이 약 2일간 서비스 중단. 유사 앱이 무제재로 운영되는 형평성 문제 제기. **스태프 답변 없음** |
| 토픽 2802 | 생년월일 운세 앱 운영자가 **타로 앱** 등록 시 반려. 반려 사유 원문: **"동일 워크스페이스 내 유사한 서비스/앱 이름/앱 아이콘으로 출시 어려운 점"**. 해결: 2주 유예 승인 받아 **두 서비스 통합** |
| 토픽 1601 | 여러 기능을 별도 앱으로 등록하는 관행에 대해 seonjeong: *"내부에서도 비슷한 의견이 나와 운영쪽에 전달해두었고 **별도의 가이드라인을 잡고 있습니다**"* |

> **함의 3가지**
> 1. 로빈식 "21개 앱 카테고리 점유" 전략은 **운세 도메인에서 재현 불가**.
> 2. 우리 컨셉(사주+MBTI+혈액형+별자리)은 **처음부터 단일 앱으로 통합**하는 것이 정책적으로도 유일한 정답이다. 이는 오히려 유리하다.
> 3. 다만 **검색 인덱스는 앱 이름 + 검색 키워드 + 첫 번째 피쳐만** 커버하므로, 단일 앱으로 4개 키워드군을 모두 잡으려면 **검색 키워드 필드에 전량 등록 + 첫 번째 피쳐 선정**이 결정적으로 중요해진다.

## 11. [D] 미실행 — 토스 앱 내 실측 프로토콜 (반드시 수행할 것)

본 조사에서 실기기 접근이 불가했다. 아래는 **다음 담당자가 그대로 수행할 측정 스펙**이다. 결과는 문서 07 미해결 항목 3번(점신 외 운세 미니앱 수)을 확정한다.

### 11.1 검색어 전수 조사

토스 앱 → 우측 하단 `전체` → 상단 검색바에 아래 12개 질의어를 순차 입력하고 결과를 **전체 스크롤 캡처**한다.

| # | 질의어 | 측정 이유 |
|---|---|---|
| 1 | `운세` | 카테고리 헤드 키워드 |
| 2 | `사주` | 코어 키워드 |
| 3 | `오늘의운세` | 띄어쓰기 없는 롱테일(토큰화 방식 확인) |
| 4 | `오늘의 운세` | 띄어쓰기 있는 변형(3번과 결과가 다르면 = 형태소 분석 없이 부분문자열 매칭) |
| 5 | `MBTI` / 6 `엠비티아이` | 영문/한글 표기 매칭 여부 |
| 7 | `별자리` / 8 `점성술` | 동의어 확장 여부 |
| 9 | `궁합` | 관계형 키워드 |
| 10 | `혈액형` | 경쟁 공백 확인 |
| 11 | `타로` | 인접 카테고리 |
| 12 | `신년운세` | 시즌 키워드 |

각 결과에 대해 기록할 필드: **노출 순서 / 미니앱 이름(잘림 여부 포함) / 제공사 / 설명 문구 / 아이콘 / 카테고리 뱃지 / 결과 총 개수**.

### 11.2 검증할 가설

| 가설 | 확인 방법 |
|---|---|
| H1. 검색은 부분문자열 매칭이다 | 3번(`오늘의운세`)과 4번(`오늘의 운세`) 결과 집합이 다르면 참 |
| H2. 검색 결과는 DAU/설치수 순 정렬이다 | 동일 키워드에서 대형 앱(점신 등)이 항상 1위인지 |
| H3. 첫 번째 피쳐가 실제로 검색된다 | 특정 앱의 기능명으로만 검색해서 그 앱이 나오는지 |
| H4. 앱 이름은 8자 근처에서 잘린다 | 결과 목록의 잘린 이름 길이를 전수 측정 |

### 11.3 미니앱홈 전수 캡처

미니앱홈 진입 → 최하단까지 스크롤 캡처. 기록: **섹션(모듈) 이름 순서 / 각 섹션의 슬롯 수 / 카테고리 목록 전체 / '운세·라이프스타일' 계열 카테고리 존재 여부 / 카테고리 내 상위 10개 앱과 그중 앱테크형 비율**(토픽 3577 주장 검증).

### 11.4 [E] 공유 실측 프로토콜

1. `getTossShareLink('intoss://<appName>', 'https://.../og.png')` 로 링크 생성 → **카카오톡 / 인스타 DM / 문자**에 각각 붙여넣고 미리보기 렌더링 캡처
2. **앱 미설치 기기**에서 링크 탭 → 스토어 랜딩까지의 단계 수와 이탈 지점 기록
3. **네비바 기본 공유** 실행 → 생성된 링크/미리보기가 1번과 어떻게 다른지 대조(문서 12의 'OG 커스텀 불가' 확정)
